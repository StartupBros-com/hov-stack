# Create a verification skill

Every serious project needs a scripted way to drive the real app and prove behavior: launch it, exercise a feature the way a user would, and capture evidence. This skill generates that as a project-local skill (`<repo>/.claude/skills/verify-<app>/`) tailored to the repo. Write the generator's output for the next agent, not for a human: it will be read cold, mid-task, by an agent that has never seen the app.

## 1. Interview the repo, not the user

Answer these from the codebase and only ask the user what you cannot observe:

- **Surface:** what does a user actually touch? A web UI, a CLI/TUI, a desktop app, an API, a mobile app, a library? A repo can have several; pick the primary one (or the one named by this skill's argument) and note the rest.
- **Run:** how does the app start locally? Prefer the repo's own documented dev command (package scripts, Makefile, README quickstart). Note ports, env vars, seed data, auth.
- **Drive:** how can an agent interact with it programmatically? Check the installed skill roster for a skill that already covers this repo's stack (for example, `~/.claude/skills/e2e-testing-for-webapps` for a Next.js, Playwright, and Supabase repo) and reuse its infrastructure rather than deriving a parallel harness. Otherwise, choose the harness in this order: an existing harness already in the repo wins (Playwright/Cypress specs, expect scripts, PTY helpers, curl-able endpoints, a debug port); then the driver `ce-test-browser` selects for this host, per its `SKILL.md` driver-selection lines; headless Playwright only when neither exists, and never installed alongside an existing browser stack; wsl-cdp only when a feature needs the operator's already-authenticated browser, and then read-only inspection unless the operator confirms a mutating drive in that session. A tmux/PTY harness drives CLI/TUI; plain HTTP drives services. The harness choice is made per repo, and the generated skill states which one it uses and why.
- **Observe:** what evidence can be captured? Screenshots, DOM/ARIA text, terminal transcripts, response bodies, logs, exit codes, DB state.
- **Isolate:** can two instances run side by side (ports, data dirs, profiles)? If not, say so in the generated skill: refusing to double-drive a shared instance beats corrupting the user's session.

If the checkout doesn't build or start as-is, fix that first (or report it precisely) before generating; a skill written against a broken base teaches wrong steps. When an irrelevant missing asset blocks startup (a static dir the API never serves, a sample config), the generated skill may create it, clearly marked as verification scaffolding, and remove it in cleanup. A missing asset the project's own build step would normally generate, such as a gitignored generated file or a compiled worker stub, is a build prerequisite rather than verification scaffolding: create the same placeholder the build produces and leave it in place. Only scaffolding invented for verification is removed in cleanup.

## 2. Generate the skill

Check the installed roster before choosing `verify-<app>`; a project skill that shadows an installed one, for example `verify-review`, gets a different app name.

Write `<repo>/.claude/skills/verify-<app>/SKILL.md` with YAML frontmatter (`name: verify-<app>`, `disable-model-invocation: true` because it starts and kills real processes and must run only when named, and a `description` that names the app, the surface, and when to reach for it -- without frontmatter the skill never registers) and these sections, each grounded in what the interview actually found (no placeholders left):

- **Launch:** the exact command that starts the app for verification, and how to tell it's ready (a log line, a port answering, a prompt). Include teardown. For a short-lived CLI or TUI there is no server to keep alive: launch means build the binary (or install deps) once, then start each drive in its own isolated PTY or tmux session.
- **Doctor:** one read-only check that answers "is this instance worth driving?": process up, right version/build, port owned by us, auth valid. Never drive an instance the verification run did not start. The doctor check must prove that (a port owned by us, a build/version stamp, a scratch data or config directory named for this run), not just that something is listening. An agent runs this first whenever anything looks off.
- **Drive:** the harness recipe with real selectors/commands from this repo, not examples. Prefer stable handles (ARIA labels, data attributes, prompt strings, route paths) over coordinates and tab order.
- **Evidence:** what to capture for a proof and where it goes. Save every artifact behind a pass claim (a screenshot, a DOM/ARIA text dump, or an exit-code log) to a fresh `/tmp/verify-<app>-<run-id>/` directory, one file per pass claim, surviving cleanup there, so a pass claim always names a path a later reader can open. When a run's proof is meant for the operator, write a short summary plus key artifacts to `<repo>/.claude/deliverables/verify-<app>/<YYYY-MM-DD-HHMM>-<slug>/`, run `open-deliverable <path>`, and report the path. State the proof standards: exercise the real user path, not internal setters or test-only endpoints; capture the action and the resulting state, not just the final screen; verify side effects (files written, rows inserted, messages sent) alongside what's visible; mocks only where a production boundary already isolates the external system. When the safe path is a dry-run or test mode, verify what it actually skips by observing (files, network, git refs) rather than trusting its name: some dry-runs still touch the network or open a browser. If the app cannot start for a reason outside the checkout (a missing credential, an unavailable service, production-only data), stop and report `environment blocked: <what>`: a distinct outcome from a mechanism failure in the generated skill itself, and in the harness outcome taxonomy this is `NO_EVIDENCE`: the gate could not be evaluated (`harness/evidence-regime.md` section 5). Never guess at a secret value to get past a blocked environment.
- **Cleanup:** how to tear down instances the run created. Never kill by process name; kill what you started. Cleanup removes instances and scratch state, never the evidence: proof artifacts under `/tmp/verify-<app>-<run-id>/`, and anything already copied to `<repo>/.claude/deliverables/verify-<app>/` for the operator, survive the teardown. A cleanup that eats the proof fails this step.
- **Helpers:** any script the skill ships is executable and its invocation is shown in the skill body. A helper the reader has to reverse-engineer is not a helper.

## 3. Seed the feature map

Create `<repo>/.claude/skills/verify-<app>/features/README.md` plus one file per user-facing feature you can identify (aim for the top 3-5 to start, from routes, commands, menus, or docs). Follow the shape in [`references/feature-map-example/`](references/feature-map-example/), with a README index and one file per feature. Each file answers, from the user's point of view: what the feature is, how to reach it, how to drive it with the harness, and what observable end state proves it works. The four H2s are `Sub-features`, `How to get to it from the user's point of view`, `Driving it with the harness`, and `Gotchas`. The map is the repo's maintained verification source; a proof that drives one convenient entry point is incomplete when the map lists others. Mark every state assumption in a feature file the proof run did not drive with an inline `unverified:` prefix, so a later run confirms it before trusting it.

## 4. Prove the generated skill before handing it over

Run its own instructions end to end once: launch, doctor, drive ONE mapped feature (one is enough; the map exists so later runs can cover the rest), capture evidence under a fresh `/tmp/verify-<app>-<run-id>/` directory (and, when it's meant for the operator, copy a summary plus key artifacts to `<repo>/.claude/deliverables/verify-<app>/<YYYY-MM-DD-HHMM>-<slug>/` and run `open-deliverable <path>`), clean up. After cleanup, confirm the evidence still exists at the named location: a cleanup that eats the proof fails this step. Fix what fails, and run the generated cleanup after every failed iteration too, so broken attempts don't strand processes and ports. Never drive an instance the verification run did not start. If the app cannot start for a reason outside the checkout, report `environment blocked: <what>` instead of forcing a run through it; that is not the same failure as a mechanism bug in the generated skill, and in the harness outcome taxonomy it is `NO_EVIDENCE`: the gate could not be evaluated (`harness/evidence-regime.md` section 5). The agent that wrote the skill also proved it, so this one proof run is self-certification: record which feature was proven, and leave every other feature file marked `unverified:` until a fresh session drives it. A generated skill that was never executed is a draft, not a deliverable.

## 5. Offer the maintenance loop

Point the user at `/maintain-verification-skill` for keeping the map honest as the app changes. Suggest a cadence only if they ask.
