# hov

Fleet mailbox for coding agents. Decision record: `docs/decisions/2026-11-10-fleet-interaction-layer.md`. Umbrella issue: hov-stack#529. This directory is PRs 1, 2 and 5 of that build order: one mailbox per host, delivery into Claude Code sessions as hook text, one outbound ssh link per peer host that carries mail between mailboxes, and the two ways an agent without a Claude Code hook (Codex, oh-my-pi) reaches the same mailbox: an MCP server it pulls from and a count-only notifier that pushes into its run.

Stdlib Python 3.9+ with an SQLite that has FTS5 (Ubuntu 24.04's 3.12 and macOS's stock 3.9 both do). No listener, no settings edits. The plugin is inert until a host enables it; nothing here runs on its own, and the link runs only where its user unit is enabled.

## Try it for one session

```bash
claude --bg -n hov-spike --plugin-dir plugins/hov
plugins/hov/scripts/hov send --to hov-spike --subject "ping" "hello from the operator session"
plugins/hov/scripts/hov ls
```

`--plugin-dir` loads the plugin for that session only. A `--bg` session starts idle (Claude Code 2.1.322 drops the positional prompt there), so hand it its first task from a peer session with the SendMessage tool, or with `claude attach`. The message reaches the session at its next prompt or tool call as a `<hov-mail>` block in `additionalContext`. The session-start event only resolves the session's name: Claude Code's `SessionStart` payload carries no `permission_mode`, so the hook cannot know there whether bodies may be injected.

The launcher lives in `scripts/`, not `bin/`, because claude.ai plugin distribution rejects a top-level `bin/`. Link it into `~/.local/bin` as `hov` when the plugin is enabled.

Observed on 2026-11-11 in two `--bg` sessions loaded through `--plugin-dir`, both with permissions bypassed. The first had a peer's message waiting before its first prompt and got the `<hov-mail host="<host>" to="hov-spike" count="1" mode="count">` block as a `hook_additional_context` attachment at `UserPromptSubmit`. The second sent itself a message as a Bash tool call and got the block at `PostToolUse` of that same call, then ran the inbox command the block named (`python3 -I` plus the script's absolute path, since `hov` was not on `PATH`) and read the body back under the untrusted-peer framing line. A trivial tool call after that had nothing attached: each message reaches a session once. `hov.log` carries the matching `deliver event=... mode=count n=1` lines. A session that bypasses permissions only ever gets the count; the block always names a runnable inbox command.

Observed the same day, with the plugin enabled through settings on two hosts: a session launched with mail already waiting got the bodies at `SessionStart` although it bypassed permissions, because that event's payload has no `permission_mode` and 0.1.0 treated an unknown mode as full. Since 0.1.1 an event that states no mode delivers nothing and records nothing, and the first prompt or tool call delivers in the mode it states (`UserPromptSubmit` and `PostToolUse` both carry it).

## Commands

| Command | What it does |
| --- | --- |
| `hov send --to ADDR [--to ADDR] [--subject S] [--thread ID] [--kind note\|task\|handoff\|reply\|status] [--importance low\|normal\|high\|urgent] BODY` | Send. `ADDR` is `name`, `host:name`, `host:*` or `*` (every session on every linked host; see Broadcasts below). `-` reads the body from stdin. Mail for another host waits here while its link is down; on a host with no hub, a send to a host no link has reached says so. A sender name, address part or thread id with a control character, `<` or `>` is refused (exit 2). |
| `hov inbox [--all] [--keep] [--json]` | Your unread mail; marks it read unless `--keep`. |
| `hov thread ID` | Every message in a thread. |
| `hov search QUERY` | FTS5 full-text search over subject and body. |
| `hov ls` | Sessions on this host (from `claude agents --json`) and known mailboxes, with unread counts, then one `link` line per peer host with its role, state and last hello, ack and inbound times. |
| `hov whoami` | Your address and how it was resolved. |
| `hov hook EVENT` | The hook entry point; reads Claude Code's hook JSON on stdin. |
| `hov mcp [--as NAME]` | MCP server on stdio (MCP 2025-06-18, newline-delimited JSON-RPC) exposing `whoami`, `inbox`, `send`, `thread`, `search` and `ls` as tools, for Codex, OMP and any MCP client. Exits 0 when the client closes stdin. |
| `hov notify --as NAME --session ID [--event E] [--json]` | Count-only delivery for an agent without a hook: prints the `<hov-mail>` count block when `ID` has mail it was not handed yet, else nothing. Never marks anything read, never prints a body, and, after a name's first poll records its first contact, writes nothing when there is nothing new. With `--json`, an object that also names the mailbox file (`db`). What `omp/hov-mail.ts` runs before turns, after tool results, and on its timer. |
| `hov link HOST [--once] [--expect-host LABEL] [--role hub\|leaf] [--remote-cmd CMD] [--via CMD]` | Keep one outbound link to `HOST` (an ssh alias) up and carry mail both ways; reconnects with capped backoff. The peer must announce `HOST`, or `--expect-host LABEL`, as its mail label. `--once` carries what is pending and exits 0 when the peer answered and both ends went idle. `--via` runs a local command instead of ssh (tests). |
| `hov relay [--role leaf\|hub]` | The far end of a link: speaks the wire on stdin/stdout. What `hov link` runs on `HOST` through ssh. |

Identity: `--as NAME`, else `$HOV_AS`, else the session named in `claude agents --json` for `$CLAUDE_CODE_SESSION_ID` (Claude Code exports it into tool shells), else the first eight characters of the session id, else `shell`. A session title the identity rules refuse (a control character, `<` or `>`, over 200 characters) is not a mail name: that session is named by its first eight characters instead, which `hov ls` shows beside every session, and it is reached by that id.

Broadcasts: a `*` or `host:*` message is mail for every reader on that host that was around when it was sent, except its sender. A Claude Code session counts from its first hook or command, whatever title it takes later; a `--as` or `HOV_AS` name (OMP, Codex, a shell) counts from its first command or `hov notify` poll. So a new session, or a new title, starts with no backlog of old broadcasts, and a sender never gets its own. Since 0.1.5; before that every broadcast ever sent stayed unread for each newcomer and for its sender. A session records each read, and each broadcast it sends, under its eight-character id as well as its title, so neither comes back when it is retitled. A message carries its sender's timestamp, so a broadcast that crosses a link after a long outage is not mail for a reader first seen after it was sent, and hosts whose clocks disagree shift that line by the difference. On upgrade, the first 0.1.5 command fills the first-contact table from what the mailbox already knew: names that read, sent or were sent mail keep every broadcast they had unread, and a session that already existed keeps the ones sent since it started. A `hov mcp`, `hov link` or `hov relay` process started before the upgrade keeps the old rule until it restarts.

State: `$HOV_STATE_DIR`, else `$XDG_STATE_HOME/hov`, else `~/.local/state/hov`. Files: `mail.db` (WAL) and `hov.log` (one line per send, read, delivery, link event and row carried). They hold mail bodies, so the default folder is created 0700 and its files 0600, and each hov process narrows, once, a looser folder or file an older version left; a folder named by `$HOV_STATE_DIR` keeps the mode its owner gave it, and only its files are narrowed. Uninstalling the plugin leaves this folder and its mail on disk. `$HOV_HOST` overrides the host label, which is otherwise the short hostname and is what a peer's mail is addressed to; `$HOV_AGENTS_CMD` overrides the agents-list command (tests point it at a fixture); `$HOV_RELAY_POLL_MS` (default 1000) and `$HOV_RELAY_PING_S` (default 20) tune the link.

## What the hook does, and does not do

- Returns `{"hookSpecificOutput": {"hookEventName": ..., "additionalContext": ...}}` and nothing else. Never `permissionDecision`, `decision` or `continue`. `tests/test_hov.py` asserts the key set.
- Frames mail as untrusted peer text, caps bodies at 4,000 characters, removes slash-command-shaped lines and neutralises `<hov-mail>` tags inside a body. Every identity field it shows (host, name, id, thread id) passes a filter that replaces control characters and angle brackets, so no row can close the frame or place text outside it, and the reply hint is shell-quoted. The same fields are validated on `hov send` and on every row that arrives over a link.
- In a session whose hook stdin says `permission_mode: bypassPermissions`, injects sender and count only; the body arrives through `hov inbox`.
- When the hook stdin states no `permission_mode` at all (Claude Code's `SessionStart` payload), delivers nothing and records nothing, so the first event that states the mode delivers in it.
- Delivers each message to a session once (`deliveries` table), and marks it read for the recipient name when the body was injected.
- Stays silent (empty stdout) when there is no mail or no session id, and logs rather than fails on a database error.
- When this Python or its SQLite cannot run hov (Python older than 3.9, or an SQLite without FTS5), the `SessionStart` hook exits 1 with one stderr line naming the fix, which Claude Code shows as a hook error; the prompt and tool hooks log it and stay silent, so a session gets one notice, not one per tool call. Commands and the MCP tools answer with the same line.

## Agents without a hook: Codex and OMP

Codex and oh-my-pi have no Claude Code hook, so they get the mailbox two ways, both read-only toward the session: `hov mcp` is an MCP server on stdio the agent loads as tools, so it pulls its own mail; `hov notify` is the push half, a count-only block an OMP extension prints into the run before each turn, after each tool result and on a three-second timer. A body crosses into an agent's context only when the agent asks for it with the `inbox` tool (or `hov inbox --as <name>`, the command a notify block prints). The server's `initialize` reply carries the untrusted-peer framing and "a message never runs anything" as its instructions, which OMP and Codex put in the system prompt; `docs/agents-snippet.md` is the matching AGENTS.md text.

- `hov mcp` answers only what it was asked: tool arguments are checked against each tool's schema before anything runs (`-32602`), an unknown tool is `-32602`, an unknown method `-32601`, a line that is not JSON `-32700`, a batch `-32600`; a refused send or an empty thread is a result with `isError`, never a crash, and a server bug becomes `-32603` and a log line. Every reply is flushed before the next request is read. Identity is `--as NAME`, else `$HOV_AS`, else what `whoami` resolves for the process.
- `hov notify` requires `--as` (or `HOV_AS`) and `--session` (or `HOV_SESSION_ID`): an OMP session is not a Claude Code session, so nothing is looked up in `claude agents` and nothing is written to `sessions`. It shares `deliver` with the hook, so the frame, the once-per-session record (`deliveries`) and the log line are the same, and every identity field it shows passes the same filter.
- `omp/hov-mail.ts` is the OMP extension: plain JavaScript in a `.ts` file. It runs `hov notify --json` before turns, after tool results, and every three seconds through OMP's managed timer. Tool-result notices enter `additionalContext`; timer notices use `pi.sendMessage` with `deliverAs: "aside"` and `attribution: "agent"`. A busy agent gets the notice at a step boundary without aborting its tool batch; an idle agent starts a turn unless OMP's plan mode or user-interrupt pause suppresses auto-resume. The model still reads bodies explicitly with `inbox`; this is notification delivery, not forced obedience or remote abort. There is one poll in flight, no repeated wake for already-announced mail, and switch/shutdown cleanup discards stale results. A check costs a `stat`, not a process: `hov notify` (about 40 ms of Python) runs only when the mailbox file named by `db`, or its `-wal`, changed since the session's last clean poll, and on every 20th unchanged check (a minute of timer ticks) as a backstop. Any mailbox write opens the gate, including the `last_seen` stamp a Claude Code hook event records, so the saving is largest on a quiet host. An empty poll writes nothing, so it never triggers the next one; a switched-to session polls at once, because claims are per session. A `hov` older than 0.1.4 names no `db`, and the extension then polls on every check. Subagents never poll. A missing `hov`, a non-zero exit or unparseable output contributes no mail. `HOV_AS` names the mailbox (default `omp`), `HOV_BIN` names the executable (default `~/.local/bin/hov` when it exists, else `hov` on `PATH`). The session id comes from OMP or one fallback id per process.
- Install by copying `omp/hov-mail.ts` into `~/.omp/agent/extensions/`, then restart OMP. In OMP 18.18.9, `/reload-plugins` refreshes discovery and MCP connections, not loaded extension code. Copying the file alone does not change an already-running session. Managed polling uses the OMP 18.18.9 extension API; hosts without managed timers retain the turn/tool-result path.
- A notification's once-per-session record is written when `hov notify` prints the block, not when OMP displays it. A failure or switch between those steps can lose that announcement, but the message remains unread and accessible through `inbox`.
- `mcp/omp.mcp.json` is the OMP server entry (`~/.omp/agent/mcp.json`); Codex takes `codex mcp add hov -- hov mcp --as codex` and, for headless `codex exec` to call the tools, `default_tools_approval_mode = "approve"` under the `[mcp_servers.hov]` stanza that command writes: headless Codex runs with `approval_policy = never` and refused the hov `inbox` call without that line (the tools carry no read-only annotation, so Codex asks, and `never` denies). The line pre-approves this server's six tools, `send` included, and nothing else in Codex's approvals; only `inbox` has been run under it, the other five are pre-approved by the same line per Codex's source. Pre-approving a server whose `send` tool posts mail is the operator's call, separate from the enabling go; interactive Codex is untested. Neither is wired by this plugin: the plugin root has no `.mcp.json`, since Claude Code sessions already have the hook and the CLI, and adding tools to a session is an enabling step. A running OMP session reconnects its servers only on its own commands: `/mcp reload`, its own `/mcp add`, `remove`, `unauth` and `reauth` (each reloads after its edit), and `/reload-plugins`. Nothing watches `mcp.json` (OMP's settings watcher covers `config.yml`, project settings and `--config` overlays), and a subagent shares its parent's servers, so neither file reaches a running session on its own.
- A count block (the hook's in a session that bypasses permissions, and every `notify`) names a sender only as a short token: a letter or digit, then up to 31 letters, digits, dots, underscores or dashes. Any other name, a title with spaces included, shows as `?`, and at most five senders are named, the rest as `+N more`. The block is pushed into context before the model has asked for anything, so a sender must not get to choose a sentence there; `hov inbox` shows the full name inside the untrusted-peer framing once the model asks. The cost: a Claude Code session's mail name is its title, and a title is words with spaces, so every titled session is `host:?` in a count block (the host still shows, and `hov inbox` names it). A token can still spell a slug such as `do-this-now`; it sits in a name slot inside a frame the skill calls untrusted peer text. The host half goes through the same rule: the link validates a peer's host to a slug of at most 64 characters, and a value stored before validation is a token or `?` like the name.
- The hook and `notify` wait at most 2 s for the write lock (`HOOK_BUSY_MS`; their callers allow 5 s). A locked database is one `hook-error` line in the log, exit 0 and no output from the hook, and one stderr line and exit 1 from `notify`, which the extension treats as no mail; nothing is claimed, and the next hook or notify delivers. The hook has written `sessions.last_seen` on every event since 0.1.1, so a hook with nothing pending still takes the write lock once, for under a millisecond; this PR leaves that as it is.
- Handing a message to a session is one write transaction (`BEGIN IMMEDIATE` on the `deliveries` row), so concurrent hooks or notifies for one session, which used to each print the block, hand it over exactly once; the one that claims nothing prints nothing. `hov ls` and the log pass every field through the same filter as the frame, so no row or peer can split a line or plant a tag there, and `hov mcp --as` is validated like a `hov send` name before anything runs.
- `hov mcp` reads a request line of at most 8 MiB (a longer one is dropped in bounded pieces and answered with one `-32600`), treats a request nested past the parser's depth as `-32700`, refuses an `id` that is not a string or an integer (`-32600`), refuses a string argument that is not valid Unicode (`-32602`, before any row is written), and escapes U+2028, U+2029 and U+0085 in every reply so a client that splits on them still sees one line.
- Proven live after merge, on a hub with the approval line above: a model inside headless Codex (`codex exec`, read-only sandbox, scratch directory) called the `inbox` tool, the call completed, and it answered with the token the waiting message asked for; the server logged the read. Also proven live after merge, in an interactive OMP session restarted so it loaded the extension and `mcp.json`: the count block appeared at its next turn, the model read its mail with the `inbox` tool, and a reply carrying the token a hub session had asked for left the `omp` mailbox and crossed the link. Not proven here: whether an OMP model acts on the block unprompted (the operator was driving that session, and the log records tool calls, not the chat), which path sent that reply (the `send` tool and the CLI write the same log line), interactive Codex, and the five hov tools Codex has not called. `tests/test_mcp.py` proves the wire and the rows; the extension is proven under node with a fake `pi` whose `exec` runs the real script, which is the same block that would enter an OMP run. Live since then in that OMP session (OMP 18.18.9), by the laptop's hov log: with a pre-merge 0.1.4 build loaded (timer and tool-result delivery, no change gate), 31 notices went out on the timer 0-3 s after they arrived, where the 15 turn-start notices before it, sent while the session was running, waited 401-5,394 s; 28 of the 31 were read within 39 s, the other three after 235, 414 and 974 s. With 0.1.4 loaded, a quiet mailbox started `hov notify` once a minute (6 runs in 318 s, not one per three-second tick), and a test note was announced on the next tick, 2.7 s after it was sent, and read about 300 s later. The log records reads, not what prompted them, so the idle wake itself (an aside starting a turn in an idle model, rather than a long step ending or a user prompt) is not shown live; nor are tool-result delivery (the timer won every race) or the plan-mode and Esc holds. Those are proven only under node with that fake `pi`.

## The cross-host link

`hov link HOST` runs `~/.local/bin/hov relay` on `HOST` through `ssh -T` and speaks newline-delimited JSON over its stdio. Nothing listens anywhere, and the wire carries rows; nothing a row says is ever run. The host that initiates is the hub; the far end is a leaf. A hub forwards to a peer what is addressed to that peer or to `*`; a leaf forwards to its hub everything not addressed to itself, so two leaves reach each other through the hub.

Every row crosses once per peer. The receiver inserts the row and its inbound mark (`relay_log`) in one transaction, commits, and only then acks; the sender records the ack in its own `relay_log`. That table doubles as the echo guard: a row received from a peer is never offered back to it. An ack lost in flight means the row is offered again after thirty seconds, and the receiver's `INSERT OR IGNORE` keeps one copy. Mail written while the link is down waits in the local mailbox and crosses when the link returns, in both directions, which replaces the reverse ssh path the decision record left open; the residual is latency, since a message written on the far host while the link is down arrives at the next connect rather than at once.

The link binds the peer's label to the host it dialed: the peer must announce `HOST` (or `--expect-host LABEL`) as its mail label and any other label is refused (`label-mismatch`), since that label decides which rows the peer is handed. It also refuses a peer that announces the hub's own label (a unit pointed at the wrong alias), a peer on another protocol number, a row that fails validation (nacked, recorded, never offered again: a timestamp within what SQLite and `datetime` both hold, encodable strings, no control character or angle bracket in any host, name, id or thread id), and a row that names this host as its origin or sender (`spoof`). `origin_host` and `from_host` on a relayed row are what the peer asserted; the ssh key is what authenticates the peer. A row too large for one wire line (4 MiB) is refused on the sending side, recorded as a local nack and never closes the link, so the rows behind it still cross. Lines that are not JSON, before or after the hello, are logged and skipped and never count as traffic, so a login banner or a runtime manager's warning on the remote's stdout does not break the link, while a peer that only ever sends noise still hits the hello timeout. When the remote command ends before saying hello, the log carries its exit code and the last lines of its stderr. `peers` holds one row per peer with its state; `hov ls` prints it.

`systemd/hov-link@.service` is the user unit, one instance per peer alias, enabled on the hub only:

```bash
ln -s "$(pwd)/plugins/hov/systemd/hov-link@.service" ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now hov-link@HOST.service
```

The unit sets the `PATH` the user manager lacks (`~/.local/bin` is not on it), and the ssh command pins `ControlMaster=no` so a shared master from an interactive shell never carries or outlives the unit's session. `network-online.target` does not exist in the user manager; the link retries with backoff (1 s doubling to 60 s) instead. The far host needs `~/.local/bin/hov` at this version and nothing else: no unit, no listener, no settings change.

What the tests prove and what they do not: `tests/test_relay.py` runs two real `hov` processes against each other over a pipe (`--via`), so the round trips, store-and-forward, dedup, echo guard, loop guard and label binding are observed on bytes that crossed between processes and on rows in two SQLite files, and the row with its inbound mark is in the receiver's database by the time its ack is read. Forwarding through a hub to a third host is proven the same way, with three mailboxes on one machine. Delivery of a relayed message into a session by the hook is proven on the leaf's mailbox with the agents fixture. A model reading relayed mail on the far host through its own Claude Code session is not proven here.

Observed on 2026-11-11 over real ssh between two hosts on one tailnet, with this branch's script staged on the far host under `/tmp` and both hosts' live mailboxes (checked first: nothing in either backlog was addressed to the other host). One message was written on each host to a unique recipient on the other, and each `hov send` printed the waits-here hint. One `hov link HOST --once` from the hub exchanged hellos, carried both rows and exited 0 in 0.2 s; each inbox then held the other host's message with its `origin_host` intact, and both `relay_log` tables held one `in` and one `out` row. A second `--once` connect, run as a transient user unit with the unit's `PATH` through `systemd-run --user`, exchanged hellos and carried nothing: both row counts were unchanged. The far host had only the staged script and `/usr/bin/python3` in a non-login ssh shell, and its hello carried `ver='0.0.0'`, since a loose copy has no VERSION file beside it. Repeated with the final script (label binding, identity validation on send and arrival, local refusal of oversize rows): a run with `--expect-host elsewhere` was refused as `label-mismatch` with exit 1, both inboxes empty and both row counts unchanged; the same command without it crossed one message each way, exit 0 in 0.2 s, and the transient-unit connect again carried nothing.
