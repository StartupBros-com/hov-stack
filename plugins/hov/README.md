# hov

Fleet mailbox for coding agents. Decision record: `docs/decisions/2026-11-10-fleet-interaction-layer.md`. Umbrella issue: hov-stack#529. This directory is PRs 1, 2, 4 and 5 of that build order: one mailbox per host, delivery into Claude Code sessions as hook text, a wake for a Claude Code session sitting idle at its prompt when direct mail reaches it, one outbound ssh link per peer host that carries mail between mailboxes, and the two ways an agent without a Claude Code hook (Codex, oh-my-pi) reaches the same mailbox: an MCP server it pulls from and a count-only notifier that pushes into its run.

Stdlib Python 3.9+ with an SQLite that has FTS5 (Ubuntu 24.04's 3.12 and macOS's stock 3.9 both do). No listener, no settings edits. The plugin is inert until a host enables it; nothing here runs on its own, and the link runs only where its user unit is enabled. Once a host enables it, each Claude Code session idle at its prompt keeps one watcher process for its idle wake (see [Idle wake](#idle-wake-claude-code)).

## Try it for one session

```bash
claude --bg -n hov-spike --plugin-dir plugins/hov
plugins/hov/scripts/hov send --to hov-spike --subject "ping" "hello from the operator session"
plugins/hov/scripts/hov ls
```

`--plugin-dir` loads the plugin for that session only. A `--bg` session runs a positional prompt as its first turn in Claude Code 2.1.323 (2.1.322 dropped it and started idle); hand it later tasks from a peer session with the SendMessage tool, or with `claude attach`. The message reaches the session at its next prompt or tool call as a `<hov-mail>` block in `additionalContext`, and a session sitting idle at its prompt is woken for it (direct mail only; see [Idle wake](#idle-wake-claude-code)). The session-start event only resolves the session's name: Claude Code's `SessionStart` payload carries no `permission_mode`, so the hook cannot know there whether bodies may be injected.

The launcher lives in `scripts/`, not `bin/`, because claude.ai plugin distribution rejects a top-level `bin/`. Link it into `~/.local/bin` as `hov` when the plugin is enabled.

Observed on 2026-11-11 in two `--bg` sessions loaded through `--plugin-dir`, both with permissions bypassed. The first had a peer's message waiting before its first prompt and got the `<hov-mail host="<host>" to="hov-spike" count="1" mode="count">` block as a `hook_additional_context` attachment at `UserPromptSubmit`. The second sent itself a message as a Bash tool call and got the block at `PostToolUse` of that same call, then ran the inbox command the block named (`python3 -I` plus the script's absolute path, since `hov` was not on `PATH`) and read the body back under the untrusted-peer framing line. A trivial tool call after that had nothing attached: each message reaches a session once. `hov.log` carries the matching `deliver event=... mode=count n=1` lines. A session that bypasses permissions only ever gets the count; the block always names a runnable inbox command.

Observed the same day, with the plugin enabled through settings on two hosts: a session launched with mail already waiting got the bodies at `SessionStart` although it bypassed permissions, because that event's payload has no `permission_mode` and 0.1.0 treated an unknown mode as full. Since 0.1.1 an event that states no mode delivers nothing and records nothing, and the first prompt or tool call delivers in the mode it states (`UserPromptSubmit` and `PostToolUse` both carry it).

## Commands

| Command | What it does |
| --- | --- |
| `hov send --to ADDR [--to ADDR] [--subject S] [--thread ID] [--kind note\|task\|handoff\|reply\|status] [--importance low\|normal\|high\|urgent] BODY` | Send. `ADDR` is `name`, `host:name`, `host:*` or `*` (every session on every linked host; see Broadcasts below). `-` reads the body from stdin. Mail for another host waits here while its link is down; on a host with no hub, a send to a host no link has reached says so. A sender name, address part or thread id with a control character, `<` or `>` is refused (exit 2). A recipient on this host that has finished and has no running process is restarted to read the mail, and `--json` adds `reach` (see [Finished sessions](#finished-sessions-claude-code)). |
| `hov inbox [--all] [--keep] [--json]` | Your unread mail; marks it read unless `--keep`. |
| `hov thread ID` | Every message in a thread. |
| `hov search QUERY` | FTS5 full-text search over subject and body. |
| `hov ls [--repo NAME] [--all]` | Sessions on this host (from `claude agents --json`) and known mailboxes, with unread counts, then one `link` line per peer host with its role, state and last hello, ack and inbound times. Each session also carries where it works: `dir` (the newest working directory its transcript recorded, else its launch directory; `dir_from` says which, or `gone` when that directory was removed), `repo` (GitHub owner/name from `origin`, else the main checkout's folder name), `branch`, `worktree` and `checkout`; the text form shows `at=repo:branch`. In `--json` a session also carries `send_to`, the name Claude Code's own SendMessage takes for it, or null when the session is not running or its title is not a usable name. `--repo` keeps only the sessions working in that repository, matched on the whole owner/name, name or checkout folder name, any case. `--all` (0.1.13) adds one `finished` row per background session that has finished and has no running process, newest first. Since 0.1.14 it carries `addr`, where `hov send` reaches it (its title when no other listed session holds it, else its 8-character id), `unread`, and `restart` (false when its launch folder is gone, `restart=no` in the text form); `send_to` stays null, and its mail is no longer shown on a second, `mailbox` row. Then facts and pointers only: `last_active` (its transcript's last timestamp), the location fields (for a removed worktree, the repository of the checkout it sat in and the branch its transcript recorded), `pr_links` (the newest five pull requests Claude Code linked to its job from the session's output, as owner/repo#N; not only ones it opened) and `pr_links_total`, `transcript`, `deliverables_written` (the newest five files still on disk that it wrote with a write tool into a `.claude/deliverables/` folder, null while unread) and `deliverables_read` (`whole`, or `tail` when only the end of a longer transcript was read; `wrote=N+` in the text form). No prompt, step, result or link title is read. Transcripts are read from the end (32 MiB each, `HOV_FINISHED_TAIL`) for about 2 s a call (`HOV_FINISHED_READ_SECONDS`), newest first, and kept in `finished.json` in the mailbox folder by size and modification time. |
| `hov ask SESSION QUESTION [--timeout S] [--json]` | One question to a read-only copy of a session's saved conversation; prints the answer and restarts nothing. `SESSION` is a name, an 8-character id or a whole session id on this host; `-` reads the question from stdin. See [Finished sessions](#finished-sessions-claude-code). |
| `hov whoami` | Your address and how it was resolved. |
| `hov hook EVENT` | The hook entry point; reads Claude Code's hook JSON on stdin. |
| `hov wake` | The Stop hook's idle watcher; reads the hook JSON on stdin and exits 86 when it claims a wake (see [Idle wake](#idle-wake-claude-code)). Not for use by hand. |
| `hov mcp [--as NAME]` | MCP server on stdio (MCP 2025-06-18, newline-delimited JSON-RPC) exposing `whoami`, `inbox`, `send`, `thread`, `search` and `ls` as tools, for Codex, OMP and any MCP client. Exits 0 when the client closes stdin. |
| `hov notify --as NAME --session ID [--event E] [--json]` | Count-only delivery for an agent without a hook: prints the `<hov-mail>` count block when `ID` has mail it was not handed yet, else nothing. Never marks anything read, never prints a body, and, after a name's first poll records its first contact, writes nothing when there is nothing new. With `--json`, an object that also names the mailbox file (`db`). What `omp/hov-mail.ts` runs before turns, after tool results, and on its timer. |
| `hov link HOST [--once] [--expect-host LABEL] [--role hub\|leaf] [--remote-cmd CMD] [--via CMD]` | Keep one outbound link to `HOST` (an ssh alias) up and carry mail both ways; reconnects with capped backoff. The peer must announce `HOST`, or `--expect-host LABEL`, as its mail label. `--once` carries what is pending and exits 0 when the peer answered and both ends went idle. `--via` runs a local command instead of ssh (tests). |
| `hov relay [--role leaf\|hub]` | The far end of a link: speaks the wire on stdin/stdout. What `hov link` runs on `HOST` through ssh. |

Identity: `--as NAME`, else `$HOV_AS`, else the session named in `claude agents --json` for `$CLAUDE_CODE_SESSION_ID` (Claude Code exports it into tool shells), else the first eight characters of the session id, else `shell`. A session title the identity rules refuse (a control character, `<` or `>`, over 200 characters) is not a mail name: that session is named by its first eight characters instead, which `hov ls` shows beside every session, and it is reached by that id.

Broadcasts: a `*` or `host:*` message is mail for every reader on that host that was around when it reached this host's mailbox, except its sender. A Claude Code session counts from its first hook or command, whatever title it takes later; a `--as` or `HOV_AS` name (OMP, Codex, a shell) counts from its first command (`hov ls`, `search` and `thread` included; `hov link` and `hov relay` carry mail and are no reader), its first `hov notify` poll, or the start of its `hov mcp` connection. A session that `hov ls` lists but that has never run hov counts from now. So a new session, or a new title, starts with no backlog of old broadcasts, and a sender never gets its own. Since 0.1.5; before that every broadcast ever sent stayed unread for each newcomer and for its sender. A session records each read, and each broadcast it sends, under its eight-character id as well as its title, so neither comes back when it is retitled. That is arrival order, never a clock reading: storing a message and recording a first contact each take the next stamp from one counter in the mailbox, so a broadcast that crosses a link after an outage is mail for every reader that was around when it arrived, whatever the sender's clock says, and a local clock that steps back changes nothing. A message still shows its sender's timestamp. On upgrade, the first 0.1.5 command fills the first-contact table from what the mailbox already knew: names that read, sent or were sent mail keep every broadcast they had unread, and a session that already existed keeps the ones sent since it started. A `hov mcp`, `hov link` or `hov relay` process started before the upgrade keeps the old rule until it restarts, and a message it stores has no arrival stamp, so it is placed by its timestamp.

State: `$HOV_STATE_DIR`, else `$XDG_STATE_HOME/hov`, else `~/.local/state/hov`. Files: `mail.db` (WAL), `hov.log` (one line per send, read, delivery, wake event, link event and row carried) and `wake/` (one file per armed idle watcher, named by its session id). They hold mail bodies, so the default folder is created 0700 and its files 0600 (`wake/` is created 0700 and each file in it 0600), and each hov process narrows, once, a looser folder or file an older version left; a folder named by `$HOV_STATE_DIR` keeps the mode its owner gave it, and only its files are narrowed. Uninstalling the plugin leaves this folder and its mail on disk. `$HOV_HOST` overrides the host label, which is otherwise the short hostname and is what a peer's mail is addressed to; `$HOV_AGENTS_CMD` overrides the agents-list command (tests point it at a fixture); `$HOV_RELAY_POLL_MS` (default 1000) and `$HOV_RELAY_PING_S` (default 20) tune the link.

## What the hook does, and does not do

- Returns `{"hookSpecificOutput": {"hookEventName": ..., "additionalContext": ...}}` and nothing else. Never `permissionDecision`, `decision` or `continue`. `tests/test_hov.py` asserts the key set.
- Frames mail as untrusted peer text, caps bodies at 4,000 characters, removes slash-command-shaped lines and neutralises `<hov-mail>` tags inside a body. Every identity field it shows (host, name, id, thread id) passes a filter that replaces control characters and angle brackets, so no row can close the frame or place text outside it, and the reply hint is shell-quoted. The hint names the first message that wants an answer; a block holding only `status` or `low` mail carries no reply hint and says no reply is expected. The same fields are validated on `hov send` and on every row that arrives over a link.
- In a session whose hook stdin says `permission_mode: bypassPermissions`, injects sender and count only; the body arrives through `hov inbox`.
- When the hook stdin states no `permission_mode` at all (Claude Code's `SessionStart` payload), delivers nothing and records nothing, so the first event that states the mode delivers in it.
- Delivers each message to a session once (`deliveries` table), and marks it read for the recipient name when the body was injected.
- Stays silent (empty stdout) when there is no mail or no session id, and logs rather than fails on a database error.
- When this Python or its SQLite cannot run hov (Python older than 3.9, or an SQLite without FTS5), the `SessionStart` hook exits 1 with one stderr line naming the fix, which Claude Code shows as a hook error; the prompt and tool hooks log it and stay silent, so a session gets one notice, not one per tool call. Commands and the MCP tools answer with the same line.
- When no `python3` is on `PATH` at all, the `SessionStart` command prints one line saying hov needs Python 3.9 or newer and exits 1, and the prompt and tool commands exit 0 with nothing on stderr. Before 0.1.8 each of the three exited 127, so a session got a hook error on every prompt and tool call. On a Mac without the developer tools, `/usr/bin/python3` is a stub that opens an install dialog; the check finds it, so such a Mac behaves as before.

## Idle wake (Claude Code)

A Claude Code session hears its mail only when one of its hooks runs, and a session sitting idle at its prompt runs none, so before 0.1.7 mail for it waited for the operator's next prompt. The Stop hook closes that gap. It runs `hov wake` as an `asyncRewake` hook, which Claude Code leaves running in the background once the turn ends. When direct mail the session was not handed arrives, the watcher claims it, writes a count block to stderr and exits 86; the hook's shell wrapper turns that exit, and only that one, into the 2 that makes Claude Code start a turn in the idle session. Any other exit (an argparse error, which is also 2, a crash, a kill, an older script with no `wake` command) becomes 0 and wakes nothing.

- What wakes a session: a direct message to one of its names that is not a broadcast (`*` or `host:*`), not kind `status`, not importance `low`, not sent by the session itself, and that the session was neither handed nor woken for already. Every filter is in the one query, so no number of other pending messages can hide one.
- What the woken turn sees: Claude Code shows a task notification titled `hov: mail from another agent`, and the turn starts from the hook's `rewakeMessage` followed by a `<hov-mail ... mode="wake">` block: the count, the senders as short tokens (the same rule as every count block), a line saying no user is waiting on the turn and that ending it without a reply is fine, and the `hov inbox` command that reads the bodies. Never a body or a subject. The woken turn's own `UserPromptSubmit` hook then delivers the mail as any prompt's does, in the mode the session runs in (sender and count only when it bypasses permissions).
- A wake grants nothing. It starts a turn, the turn runs under the session's own permissions, and a body reaches the model, framed as untrusted peer text, only when the model asks for it or the session's mode already allows it.
- Bounds, per session: one wake per 30 s, 12 per hour and 48 per day, charged in the same write transaction that claims the messages. Two idle sessions that answer each other's mail with nobody prompting either therefore trade at most that many woken turns. The caps do not cover a busy turn: mail that arrives while a session is working is delivered by that turn's own hooks, with no wake and no cap, so two sessions kept busy by each other's mail are not bounded by hov. Bound that at the sender (hov-stack's `peer-loop-guard` hook refuses the 9th reply in a row with no work in between). A clock that steps back counts as inside the cooldown and both windows, so it can delay a wake but never add one. A watcher whose hour or day is spent stays armed, logs `wake-spent` once and fires when the window frees; meanwhile the session's next prompt delivers the mail as before.
- One watcher per session, recorded as a file in the state directory's `wake/`. A newer Stop's watcher replaces the older one; the session's next prompt or main-thread tool call retires it (a subagent's tool call does not); a new session id in the same Claude Code process (`/clear`, `/resume`) retires the old id's. A watcher also ends on its own when its Claude Code process is gone (`wake-orphan`), on SIGTERM, SIGHUP or SIGINT (`wake-stopped`; `claude stop` sends SIGTERM), and a minute before the hook's four-hour timeout (`wake-expired`). A session idle longer than that is not woken, and its next prompt delivers the mail. A watcher killed outright leaves its file, which the next `SessionStart` on the host removes.
- Where it does not arm: `HOV_WAKE=0`; any entrypoint but `cli` (an interactive or `--bg` session), so not the SDKs, IDE extensions or `claude -p`, where an exit-2 Stop hook starts another turn and the run would never end; a `-p` run that reports `cli` anyway; a session id that is not a plain file name; a host without `/proc`; and a Claude Code older than 2.1.319, or whose version the watcher cannot read, where the hook would run in the foreground and hold the turn open (logged as `wake-skip`). Linux only: the watcher finds its Claude Code process, that process's start time and its version in `/proc`. The version comes from the process name or the executable's name (the native installer runs `.../claude/versions/<version>`), or, for an npm install, from the `package.json` of `@anthropic-ai/claude-code` beside the script it runs. The npm path has no test and no live run.
- Cost: one Python process per session idle at its prompt, measured here at 22 MB resident and no CPU time the kernel counted over 10 idle seconds. Each 1 s tick is a `stat` of `mail.db` and its `-wal`; the mailbox is queried, read-only, when either changed and on every 20th tick otherwise. Every hook event of every session on the host writes the mailbox, so on a busy host a watcher queries once a tick: with another session's hook firing every 0.5 s and the mailbox at ten times the workstation's rows, it used 0.01 s of CPU over 20 s (0.05% of one core), 0.2 ms a query.
- Knobs, read from the session's environment: `HOV_WAKE=0` turns it off; `HOV_WAKE_COOLDOWN_S` (30), `HOV_WAKE_CAP` (12 an hour) and `HOV_WAKE_DAY_CAP` (48 a day; either cap at 0 stops waking); `HOV_WAKE_TICK_MS` (1000); `HOV_WAKE_TTL_S` (14,340; keep it under the hook's 14,400 s timeout, or the timeout kills the watcher and its file waits for the next `SessionStart`).
- `hov.log` carries `wake-arm`, `wake-fire` (with the message ids), `wake-spent`, `wake-orphan`, `wake-stopped`, `wake-expired`, `wake-skip` and `wake-error` lines.

Observed on 2026-11-13 (UTC) with Claude Code 2.1.323, in `--bg` sessions started with `--plugin-dir` on this branch, permissions bypassed, against a scratch state directory:

- A session sitting idle was sent one direct message from a shell. Its watcher fired, the session started a turn from the count block alone, ran the `hov inbox` command the block named, and replied as the body asked. `hov.log` shows `wake-fire` and, in the same second, `deliver event=UserPromptSubmit mode=count` for the same message: the woken turn's prompt hook ran.
- Two sessions told to answer each other's mail, with the hourly cap at 3 and the cooldown at 5 s, and one message to start them: each was woken three times, then the next watcher logged `wake-spent` and the exchange stopped with nobody prompting either. All seven wakes of these runs were followed by a `UserPromptSubmit` delivery of the same message.
- `claude -p` with the plugin loaded: the Stop hook ran and finished with status 0 in 41 ms (`--debug hooks`), no watcher armed, and the run exited 0 in 5 s.
- `claude stop` on idle sessions: with the first build, the watchers died without removing their files. With the signal handling in this release, the watcher logged `wake-stopped ... signal=15` and removed its file, no watcher process was left, and that session's `SessionStart` had already removed the earlier sessions' leftover files.

Not shown live: a hook timeout ending a watcher, the npm version path, `/clear` or `/resume` in a live session, and a wake for mail that crossed a link (the watcher reads the same mailbox the link writes). The unit tests cover a new session id in the same process; nothing tests the timeout, the npm path or a relayed message waking a session. The decision record's other idle-wake candidate, a `hov channel` MCP server, was not built or tested.

## Finished sessions (Claude Code)

A background session that finished its turn keeps an idle process for about an hour, and Claude Code's own SendMessage and the idle wake above both reach it. Then Claude Code stops the process. `claude agents --json --all` still lists the session (state `done`, no `pid` or `status`), SendMessage answers `No agent named '...' is reachable`, and before 0.1.14 mail for it waited for a start nobody asked for.

How mail to a session on this host gets read, by the state `hov send` finds the recipient in:

| Recipient | What happens |
| --- | --- |
| Running, mid-turn | Its PostToolUse hook hands the mail over at its next tool call. |
| Running, idle, watcher armed | The idle wake starts a turn. |
| Running, idle, no watcher (`HOV_WAKE=0`, limits spent, an entrypoint that does not arm) | The mail waits for its next prompt. `send` says so and prints the name Claude Code's SendMessage takes for it. |
| Finished: `done`, no process | `send` restarts it to read the mail. |
| No process and not `done` (waiting on its user, or died mid-turn) | Not restarted: a restart would clear what the agents view shows about it. The mail waits and `send` says so. |
| Finished, launch folder gone | Not restarted: Claude Code refuses, and keeps the text for a later start. The mail waits. |
| Two or more sessions with no process answer to the name | None is restarted. `send` lists their 8-character ids; address one. |
| Addressed by its whole session id | Nothing is restarted: a session reads mail sent to its name or its 8-character id. `send` names the id to use. |
| On another host | The mail crosses the link. Nothing is restarted there. |

- The restart is `claude --bg --resume <session id> <text>`, run from the session's launch folder with stdin closed and a 20 s limit. Claude Code 2.1.257 or later continues the session under its own id, name, permission mode and model; hov reads `claude --version` first and restarts nothing on an older one, which would start a copy under a new id. If a copy is started anyway (the session turned out to be running), hov stops the copy and says so.
- The text is one fixed sentence of hov's own. The sender's subject and body never leave the mailbox: they reach the restarted turn as any mail does, in full in a session that asks for permission and as a count in one that bypasses permissions, which then runs `hov inbox`. `hov inbox` now ends with the reply command the full block ends with.
- A restart grants nothing. The mail is untrusted peer text, so the session acts on a request only if it fits its own task, and it runs under its own permission mode: in a session that asks for permission, a tool call waits for its user in the agents view.
- What restarts a session: the `hov send` command only, for direct mail that would wake an idle session (not kind `status`, not importance `low`, not a broadcast, not the sender's own). The MCP `send` tool and mail arriving over a link restart nothing, so every restart is one command that a host's own hooks can see and count.
- Bounds: a restart is charged to the session's wake budget (one per 30 s, 12 an hour, 48 a day, shared with the idle wake) before Claude Code is run, so a refused restart costs one too. `HOV_RESTART=0` in the sender's environment turns restarts off. An error while reaching a recipient (a locked mailbox, a Claude Code that misbehaves) never fails the send: the mail is stored, the ids are printed and that recipient's `reach` entry says `error`.
- Cost: a restarted session loads its whole conversation, as any resumed session does.
- `hov ask SESSION "QUESTION"` restarts nothing. It runs `claude -p --resume <id> --fork-session --no-session-persistence --tools Read,Grep,Glob --strict-mcp-config --permission-mode dontAsk --max-turns 20` with the question framed as peer text, prints the copy's answer on stdout and a line on stderr with the seconds and input tokens it took. The original is not restarted, interrupted or told, and its mail is not read (hov's hooks do nothing inside the copy). The copy runs in the session's launch folder (the caller's when that folder is gone) and can read files under it; under `dontAsk` a read anywhere else is refused unless the host's permission rules allow it. It cannot run a command or send anything, so an ask cannot start another. The answer is what the session believed when it stopped. A question that is empty, holds a NUL or is not UTF-8 text is refused with exit 2.
- The PostToolUse hook adds one line of hov's own after two of Claude Code's tools: after `ListAgents`, how many finished sessions that list leaves out, with the `ls --all`, `send` and `ask` commands; after a `SendMessage` whose response says nobody was reachable, when the session it named has no process, what that session is and how to reach it. No other tool call costs a listing, and nothing a peer wrote is in either line. The listing is given 2 s; it and the hook's lookup of its own session's name end by one 3.5 s deadline, so two hung listings cost the line and the lookup, and the mail is still handed over inside the hook's 5 s. `HOV_REACH_NOTES=0` turns both off.
- `HOV_CLAUDE_CMD` names the Claude Code command (default `claude`). Where `HOV_AGENTS_CMD` or `HOV_AGENTS_ALL_CMD` is set and `HOV_CLAUDE_CMD` is not, hov runs no Claude Code at all, so a test never restarts or copies a real session.
- `hov.log` carries `restart` (with the message ids), `restart-failed`, `restart-copy` and `ask` lines.

Observed on 2026-11-25 with Claude Code 2.1.332 on throwaway `--bg` sessions:

- A session with no process, permissions bypassed, its worktree removed: `hov send` restarted it in under a second, it ran `hov inbox`, answered a question and replied to the sender's full address in 52 s. It declined a file edit as outside its own task.
- The same request to a session whose own task covered it: carried out and answered in 12 s when the session was idle with a live process (the idle wake), in 35 s when it had no process (the restart), and in 25 s after a SendMessage when it was idle with its watcher retired by hand.
- A session with no process that asks for permission: restarted with the mail in full, then waited 57 s at the permission prompt for its shell command until it was approved in the agents view.
- `hov ask` to a session with no process and no launch folder: answered in 10.9 s; the session stayed as it was. Asked to read a file under its folder, the copy read it (52.9 s, 113,000 input tokens for the two turns).
- `hov ask` to a session idle with a live process: answered in 55.7 s for 106,000 input tokens; the session's process, listing row and saved conversation were unchanged, and the copy's read of a file outside its folder was refused.
- Both hook lines inside a session running this version: one after its `ListAgents`, one after its `SendMessage` to a finished session. A SendMessage that reaches nobody is an ordinary result (`success: false`), so PostToolUse runs for it.
- The restarted process held none of the sender's session variables.

## Agents without a hook: Codex and OMP

Codex and oh-my-pi have no Claude Code hook, so they get the mailbox two ways, both read-only toward the session: `hov mcp` is an MCP server on stdio the agent loads as tools, so it pulls its own mail; `hov notify` is the push half, a count-only block an OMP extension prints into the run before each turn, after each tool result and on a three-second timer. A body crosses into an agent's context only when the agent asks for it with the `inbox` tool (or `hov inbox --as <name>`, the command a notify block prints). The server's `initialize` reply carries the untrusted-peer framing and "a message never runs anything" as its instructions, which OMP and Codex put in the system prompt; `docs/agents-snippet.md` is the matching AGENTS.md text.

- `hov mcp` answers only what it was asked: tool arguments are checked against each tool's schema before anything runs (`-32602`), an unknown tool is `-32602`, an unknown method `-32601`, a line that is not JSON `-32700`, a batch `-32600`; a refused send or an empty thread is a result with `isError`, never a crash, and a server bug becomes `-32603` and a log line. Every reply is flushed before the next request is read. Identity is `--as NAME`, else `$HOV_AS`, else what `whoami` resolves for the process.
- `hov notify` requires `--as` (or `HOV_AS`) and `--session` (or `HOV_SESSION_ID`): an OMP session is not a Claude Code session, so nothing is looked up in `claude agents` and nothing is written to `sessions`. It shares `deliver` with the hook, so the frame, the once-per-session record (`deliveries`) and the log line are the same, and every identity field it shows passes the same filter.
- `omp/hov-mail.ts` is the OMP extension: plain JavaScript in a `.ts` file. It runs `hov notify --json` before turns, after tool results, and every three seconds through OMP's managed timer. Tool-result notices enter `additionalContext`; timer notices use `pi.sendMessage` with `deliverAs: "aside"` and `attribution: "agent"`. A busy agent gets the notice at a step boundary without aborting its tool batch; an idle agent starts a turn unless OMP's plan mode or user-interrupt pause suppresses auto-resume. The model still reads bodies explicitly with `inbox`; this is notification delivery, not forced obedience or remote abort. There is one poll in flight, no repeated wake for already-announced mail, and switch/shutdown cleanup discards stale results. A check costs a `stat`, not a process: `hov notify` (about 40 ms of Python) runs only when the mailbox file named by `db`, or its `-wal`, changed since the session's last clean poll, and on every 20th unchanged check (a minute of timer ticks) as a backstop. Any mailbox write opens the gate, including the `last_seen` stamp a Claude Code hook event records, so the saving is largest on a quiet host. An empty poll writes nothing, so it never triggers the next one; a switched-to session polls at once, because claims are per session. A `hov` older than 0.1.4 names no `db`, and the extension then polls on every check. Subagents never poll. A missing `hov`, a non-zero exit or unparseable output contributes no mail. `HOV_AS` names the mailbox (default `omp`), `HOV_BIN` names the executable (default `~/.local/bin/hov` when it exists, else `hov` on `PATH`). The session id comes from OMP or one fallback id per process.
- Install by copying `omp/hov-mail.ts` into `~/.omp/agent/extensions/`, then restart OMP. In OMP 18.18.9, `/reload-plugins` refreshes discovery and MCP connections, not loaded extension code. Copying the file alone does not change an already-running session. Managed polling uses the OMP 18.18.9 extension API; hosts without managed timers retain the turn/tool-result path.
- A notification's once-per-session record is written when `hov notify` prints the block, not when OMP displays it. A failure or switch between those steps can lose that announcement, but the message remains unread and accessible through `inbox`.
- `mcp/omp.mcp.json` is the OMP server entry (`~/.omp/agent/mcp.json`); Codex takes `codex mcp add hov -- hov mcp --as codex` and, for headless `codex exec` to call the tools, `default_tools_approval_mode = "approve"` under the `[mcp_servers.hov]` stanza that command writes: headless Codex runs with `approval_policy = never` and refused the hov `inbox` call without that line (the tools carry no read-only annotation, so Codex asks, and `never` denies). The line pre-approves this server's six tools, `send` included, and nothing else in Codex's approvals; only `inbox` has been run under it, the other five are pre-approved by the same line per Codex's source. Pre-approving a server whose `send` tool posts mail is the operator's call, separate from the enabling go; interactive Codex is untested. Neither is wired by this plugin: the plugin root has no `.mcp.json`, since Claude Code sessions already have the hook and the CLI, and adding tools to a session is an enabling step. A running OMP session reconnects its servers only on its own commands: `/mcp reload`, its own `/mcp add`, `remove`, `unauth` and `reauth` (each reloads after its edit), and `/reload-plugins`. Nothing watches `mcp.json` (OMP's settings watcher covers `config.yml`, project settings and `--config` overlays), and a subagent shares its parent's servers, so neither file reaches a running session on its own.
- A count block (the hook's in a session that bypasses permissions, and every `notify`) names a sender only as a short token: a letter or digit, then up to 31 letters, digits, dots, underscores or dashes. Any other name, a title with spaces included, shows as `?`, and at most five senders are named, the rest as `+N more`. The block is pushed into context before the model has asked for anything, so a sender must not get to choose a sentence there; `hov inbox` shows the full name inside the untrusted-peer framing once the model asks. The cost: a Claude Code session's mail name is its title, and a title is words with spaces, so every titled session is `host:?` in a count block (the host still shows, and `hov inbox` names it). A token can still spell a slug such as `do-this-now`; it sits in a name slot inside a frame the skill calls untrusted peer text. The host half goes through the same rule: the link validates a peer's host to a slug of at most 64 characters, and a value stored before validation is a token or `?` like the name.
- The hook and `notify` wait at most 2 s for the write lock (`HOOK_BUSY_MS`; their callers allow 5 s). A locked database is one `hook-error` line in the log, exit 0 and no mail from the hook (since 0.1.15 it still writes the line it owes a ListAgents or an unreached SendMessage, which needs no mailbox), and one stderr line and exit 1 from `notify`, which the extension treats as no mail; nothing is claimed, and the next hook or notify delivers. From 0.1.1 to 0.1.15 the hook wrote `sessions.last_seen` on every event, so every tool call of every session took the write lock, and its commit synced the WAL to disk while holding it (SQLite's default, `synchronous=FULL`): 13 to 17 ms on a healthy disk, as long as the disk takes on a busy one, with every other hook waiting behind it. Since 0.1.16 a known session with no mail only reads: the hook writes on first contact, when the name lookup is due (SessionStart, or 30 s since the last), when the session's directory changes, and to claim a delivery. `sessions.last_seen` and `sessions.cwd` are therefore as of the session's last write, up to 30 s before its last event; no command reads either. The connections the hook, `notify`, the idle watcher and the restart budget open (`db_hook`) also commit at `synchronous=NORMAL`, so those writes no longer wait for the disk under the lock. They are bookkeeping (session rows, claims, read marks, the wake budget): after a power cut or an operating-system crash the last of them may be missing, and a message may be handed over or shown unread a second time. A process that dies loses nothing, and the database stays consistent. Every other connection stays at FULL: `send`, the link and the MCP server, which store mail, and the commands a person or an agent runs (`inbox`, `ls`, `whoami`), which also write a session row. SQLite still syncs the header of a WAL it has just created or restarted, under the lock, whatever the setting: on a host where no long-lived process (`hov mcp`, `hov link`) keeps the mailbox open, each hook that writes pays that one sync.
- Handing a message to a session is one write transaction (`BEGIN IMMEDIATE` on the `deliveries` row), so concurrent hooks or notifies for one session, which used to each print the block, hand it over exactly once; the one that claims nothing prints nothing. `hov ls` and the log pass every field through the same filter as the frame, so no row or peer can split a line or plant a tag there, and `hov mcp --as` is validated like a `hov send` name before anything runs.
- `hov mcp` reads a request line of at most 8 MiB (a longer one is dropped in bounded pieces and answered with one `-32600`), treats a request nested past the parser's depth as `-32700`, refuses an `id` that is not a string or an integer (`-32600`), refuses a string argument that is not valid Unicode (`-32602`, before any row is written), and escapes U+2028, U+2029 and U+0085 in every reply so a client that splits on them still sees one line.
- Proven live after merge, on a hub with the approval line above: a model inside headless Codex (`codex exec`, read-only sandbox, scratch directory) called the `inbox` tool, the call completed, and it answered with the token the waiting message asked for; the server logged the read. Also proven live after merge, in an interactive OMP session restarted so it loaded the extension and `mcp.json`: the count block appeared at its next turn, the model read its mail with the `inbox` tool, and a reply carrying the token a hub session had asked for left the `omp` mailbox and crossed the link. Not proven here: whether an OMP model acts on the block unprompted (the operator was driving that session, and the log records tool calls, not the chat), which path sent that reply (the `send` tool and the CLI write the same log line), interactive Codex, and the five hov tools Codex has not called. `tests/test_mcp.py` proves the wire and the rows; the extension is proven under node with a fake `pi` whose `exec` runs the real script, which is the same block that would enter an OMP run. Live since then in that OMP session (OMP 18.18.9), by the laptop's hov log: with a pre-merge 0.1.4 build loaded (timer and tool-result delivery, no change gate), 31 notices went out on the timer 0-3 s after they arrived, where the 15 turn-start notices before it, sent while the session was running, waited 401-5,394 s; 28 of the 31 were read within 39 s, the other three after 235, 414 and 974 s. ## The cross-host link

`hov link HOST` runs `~/.local/bin/hov relay` on `HOST` through `ssh -T` and speaks newline-delimited JSON over its stdio. Nothing listens anywhere, and the wire carries rows; nothing a row says is ever run. The host that initiates is the hub; the far end is a leaf. A hub forwards to a peer what is addressed to that peer or to `*`; a leaf forwards to its hub everything not addressed to itself, so two leaves reach each other through the hub.

Every row crosses once per peer. The receiver inserts the row and its inbound mark (`relay_log`) in one transaction, commits, and only then acks; the sender records the ack in its own `relay_log`. That table doubles as the echo guard: a row received from a peer is never offered back to it. An ack lost in flight means the row is offered again after thirty seconds, and the receiver's `INSERT OR IGNORE` keeps one copy. Mail written while the link is down waits in the local mailbox and crosses when the link returns, in both directions, which replaces the reverse ssh path the decision record left open; the residual is latency, since a message written on the far host while the link is down arrives at the next connect rather than at once.

The link binds the peer's label to the host it dialed: the peer must announce `HOST` (or `--expect-host LABEL`) as its mail label and any other label is refused (`label-mismatch`), since that label decides which rows the peer is handed. It also refuses a peer that announces the hub's own label (a unit pointed at the wrong alias), a peer on another protocol number, a row that fails validation (nacked, recorded, never offered again: a timestamp within what SQLite and `datetime` both hold, encodable strings, no control character or angle bracket in any host, name, id or thread id), and a row that names this host as its origin or sender (`spoof`). `origin_host` and `from_host` on a relayed row are what the peer asserted; the ssh key is what authenticates the peer. A row too large for one wire line (4 MiB) is refused on the sending side, recorded as a local nack and never closes the link, so the rows behind it still cross. Lines that are not JSON, before or after the hello, are logged and skipped and never count as traffic, so a login banner or a runtime manager's warning on the remote's stdout does not break the link, while a peer that only ever sends noise still hits the hello timeout. When the remote command ends before saying hello, the log carries its exit code and the last lines of its stderr. `peers` holds one row per peer with its state; `hov ls` prints it.

`systemd/hov-link@.service` is the user unit, one instance per peer alias, enabled on the hub only:

```bash
ln -s "$(pwd)/plugins/hov/systemd/hov-link@.service" ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now hov-link@HOST.service
```

The unit sets the `PATH` the user manager lacks (`~/.local/bin` is not on it), and the ssh command pins `ControlMaster=no` so a shared master from an interactive shell never carries or outlives the unit's session. `network-online.target` does not exist in the user manager; the link retries with backoff (1 s doubling to 60 s) instead. The far host needs `~/.local/bin/hov` at this version and nothing else: no unit, no listener, no settings change.

What the tests prove and what they do not: `tests/test_relay.py` runs two real `hov` processes against each other over a pipe (`--via`), so the round trips, store-and-forward, dedup, echo guard, loop guard and label binding are observed on bytes that crossed between processes and on rows in two SQLite files, and the row with its inbound mark is in the receiver's database by the time its ack is read. Forwarding through a hub to a third host is proven the same way, with three mailboxes on one machine. Delivery of a relayed message into a session by the hook is proven on the leaf's mailbox with the agents fixture. A model reading relayed mail on the far host through its own Claude Code session is not proven here.

Observed on 2026-11-11 over real ssh between two hosts on one tailnet, with this branch's script staged on the far host under `/tmp` and both hosts' live mailboxes (checked first: nothing in either backlog was addressed to the other host). One message was written on each host to a unique recipient on the other, and each `hov send` printed the waits-here hint. One `hov link HOST --once` from the hub exchanged hellos, carried both rows and exited 0 in 0.2 s; each inbox then held the other host's message with its `origin_host` intact, and both `relay_log` tables held one `in` and one `out` row. A second `--once` connect, run as a transient user unit with the unit's `PATH` through `systemd-run --user`, exchanged hellos and carried nothing: both row counts were unchanged. The far host had only the staged script and `/usr/bin/python3` in a non-login ssh shell, and its hello carried `ver='0.0.0'`, since a loose copy has no VERSION file beside it. Repeated with the final script (label binding, identity validation on send and arrival, local refusal of oversize rows): a run with `--expect-host elsewhere` was refused as `label-mismatch` with exit 1, both inboxes empty and both row counts unchanged; the same command without it crossed one message each way, exit 0 in 0.2 s, and the transient-unit connect again carried nothing.
