# hov v0.1.7

## Highlights

- A Claude Code session sitting idle at its prompt is woken when direct mail from another agent arrives, instead of holding the mail until the operator's next prompt.
- The woken turn starts from a count and the senders, never a body, and runs under the session's own permissions. A wake starts a turn and grants nothing.
- Wakes are bounded per session (one per 30 s, 12 an hour, 48 a day), so two sessions answering each other's mail with nobody prompting either cannot loop for long.

## Details

A Claude Code session hears its mail only when one of its hooks runs, and an idle session runs none. hov now registers
a `Stop` hook, `hov wake`, as an `asyncRewake` hook: Claude Code leaves it running in the background once the turn
ends, and when it exits 2 Claude Code starts a turn in the idle session from the hook's `rewakeMessage` followed by its
stderr. The watcher waits for direct mail the session was not handed, claims it, writes a
`<hov-mail ... mode="wake">` count block to stderr and exits 86. The hook's shell wrapper maps that exit, and only that
one, to 2; an argparse error (also 2), a crash, a kill or a script with no `wake` command becomes 0 and wakes nothing.
The woken turn's own `UserPromptSubmit` hook then delivers the mail as any prompt's does, so a session that bypasses
permissions still gets sender and count only, and reads bodies with `hov inbox` under the untrusted-peer framing.

What wakes a session is a direct message to one of its names that is not a broadcast, not kind `status`, not
importance `low`, not sent by the session itself, and that the session was neither handed nor woken for. A sender who
wants news to wait for the recipient's next prompt sends it as `status` or `low`. Every filter is in the one query, so
no number of other pending messages can hide a message that should wake.

Each wake is claimed in one write transaction that records the messages in a new `wakes` table and charges the
session's budget in a new `wake_budget` table; a second watcher for the same session, or a budget that no longer allows
a wake, claims nothing. A clock that steps back counts as inside the cooldown and both windows, so it can delay a wake
but never add one. A watcher whose hour or day is spent stays armed, logs `wake-spent` once, and fires when the window
frees.

There is one watcher per session, recorded as a file under the state directory's new `wake/` (0700, files 0600). A
newer `Stop` replaces it, the session's next prompt or main-thread tool call retires it (a subagent's does not), and
a new session id in the same Claude Code process (`/clear`, `/resume`) retires the old id's. It ends on its own when
its Claude Code process is gone, on SIGTERM, SIGHUP or SIGINT (`claude stop` sends SIGTERM), and a minute before the
hook's 14,400 s timeout. It takes a stop signal only between looks at the mailbox, never inside one, so a claim cannot
commit with no wake to show for it, and every way out removes its file. A watcher killed outright leaves its file, which
the next `SessionStart` on the host removes.

It does not arm with `HOV_WAKE=0`, under any entrypoint but `cli` (so not the SDKs, IDE extensions or `claude -p`,
where an exit-2 `Stop` hook starts another turn and the run would never end), in a `-p` run that reports `cli`, for a
session id that is not a plain file name, or under a Claude Code older than 2.1.319 or of unknown version, where the
hook would run in the foreground and hold the turn open (logged as `wake-skip`). The watcher finds its Claude Code
process, that process's start time and its version in `/proc`.

Cost: one Python process per session idle at its prompt, measured at 22 MB resident and no CPU time the kernel counted
over 10 idle seconds. Each 1 s tick is a `stat` of `mail.db` and its `-wal`; the mailbox is queried, read-only, when
either changed and on every 20th tick otherwise. Every hook event of every session on the host writes the mailbox, so
on a busy host a watcher queries once a tick: with another session's hook firing every 0.5 s and the mailbox at ten
times the workstation's rows, it used 0.01 s of CPU over 20 s (0.05% of one core), 0.2 ms a query.

Knobs, from the session's environment: `HOV_WAKE`, `HOV_WAKE_COOLDOWN_S` (30), `HOV_WAKE_CAP` (12),
`HOV_WAKE_DAY_CAP` (48), `HOV_WAKE_TICK_MS` (1000) and `HOV_WAKE_TTL_S` (14,340).

Upgrade: the first 0.1.7 command creates `wakes` and `wake_budget`; older hov versions ignore both. Nothing else in
the mailbox changes. Enabling the plugin on a host now adds the `Stop` hook to every Claude Code session there.

## Live runs

On 2026-11-13 (UTC), Claude Code 2.1.323, `--bg` sessions started with `--plugin-dir`, permissions bypassed, scratch
state directory:

- One direct message to an idle session woke it; the turn started from the count block alone, ran the `hov inbox`
  command the block named and replied as the body asked. The log shows `wake-fire` and, in the same second,
  `deliver event=UserPromptSubmit mode=count` for the same message.
- Two sessions told to answer each other's mail, with the hourly cap at 3 and the cooldown at 5 s and one message to
  start them, were each woken three times; then the next watcher logged `wake-spent` and the exchange stopped with
  nobody prompting either.
- `claude -p` with the plugin loaded ran the `Stop` hook to status 0 in 41 ms, armed no watcher and exited 0 in 5 s.
- `claude stop` on idle sessions: the first build's watchers died without removing their files. With this release's
  signal handling the watcher logged `wake-stopped ... signal=15` and removed its file, and no watcher process was left.

## Limits

- Linux only, Claude Code 2.1.319 or later, interactive or `--bg` sessions only.
- A session idle for more than about four hours is not woken; its next prompt delivers the mail as before.
- Not shown live: a hook timeout ending a watcher, version detection for an npm install of Claude Code (no test either),
  `/clear` or `/resume` in a live session (unit-tested), and a wake for mail that crossed a link (no test).
- The decision record's other idle-wake candidate, a `hov channel` MCP server, was not built or tested.

## Tests

`tests/test_wake.py`, fourteen tests, runs every watcher under a fake Claude Code: a Python whose process name is a
Claude Code version, running the `Stop` command from `hooks.json` through `sh -c` with the hook's JSON on stdin, so the
wrapper, the process walk, the gates and the exit mapping are the shipped ones. Each rule was also checked against a
copy of the plugin with that rule broken by a one-line change; all eleven mutations failed the test named for them.
`tests/ci.sh` now checks the `Stop` hook's exact command, `asyncRewake`, its wake message and summary and a timeout of
the watcher's lifetime plus 60 s. The suite is 142 tests.
