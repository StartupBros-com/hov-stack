# hov v0.1.16

## Highlights

- hov's hook no longer locks the mailbox on every tool call: a session with no mail only reads. "database is locked" hook errors should become rare on a busy host.
- When the hook does write, it no longer waits for the disk while holding the lock.

## Details

### What was wrong

From 0.1.1 to 0.1.15 every hook event wrote `sessions.last_seen`, which no command reads. So every prompt and every tool call of every session took the mailbox's write lock. hov never set `PRAGMA synchronous`, so each of those commits ran at SQLite's default, FULL: it synced the WAL to disk, and the mailbox folder with it, before releasing the lock. A trace of one hook shows both syncs between taking the lock and dropping it, 13 to 17 ms together on a quiet disk.

When the disk is slow a sync takes far longer, and every other hook waits behind it. A hook waits 2 s (`HOOK_BUSY_MS`), then logs `hook-error ... err=database is locked` and gives up, with no mail delivered by that hook.

One host with about 30 sessions on one mailbox logged 9,457 of these errors in 569,952 tool calls over 14 days (16.6 per 1,000), and 75.8 per 1,000 on its worst day.

How slow the disk was in the bad windows is worked out from that host's history, not recorded live. In its ten worst 10-minute windows tool calls arrived at about one a second and 16% to 53% of their hooks failed. Replaying those arrival times through a one-lock queue, a hold of 300 ms per hook loses between 0 and 16 hooks per window where the log shows 116 to 331. Matching the log takes holds of 0.4 to 2.2 s. So in those windows a commit's syncs were taking around a second or more, and the hook that happened to be committing held the lock that long. Elsewhere the calls came faster: the median error had six tool calls in the 5 s before it, and there shorter syncs are enough.

Both shapes reproduce in a scratch mailbox with every sync delayed by a preloaded shim (a FULL commit makes two, so the lock is held for about twice the delay), one connection kept open as `hov mcp` or `hov link` keeps one, and 12 sessions:

| sync delay, hooks a second | 0.1.15 | read first only | NORMAL only | 0.1.16 (both) |
|---|---|---|---|---|
| 700 ms, 1 | 38 of 120 failed (32%) | 1 failed, p95 2,397 ms | 0, p95 77 ms | 0, p95 77 ms |
| 300 ms, 1 | 0 of 60 failed, median 681 ms | 0, p95 675 ms | 0, p95 61 ms | 0, p95 77 ms |
| 300 ms, 3 | 83 of 180 failed (46%) | 0, p95 701 ms | 0, p95 58 ms | 0, p95 70 ms |
| 300 ms, 6 | 260 of 360 failed (72%) | 0, p95 667 ms, max 1,207 ms | 0, p95 58 ms | 0, p95 68 ms |

Not yet shown: a recording of a failing window on the live host. A probe sampling the lock there saw holds of up to 359 ms, each a hook waiting on the disk, and timed syncs of up to 1,009 ms on the same filesystem, but the disk stayed quick and no error was logged while it ran. The before and after error rates for that host, and a control that replays its old traffic against 0.1.15 on the same disk, are on issue 925.

### What changed

**A known session with nothing to record only reads.** The hook now answers "which session is this" from a plain read when the session is known, its name lookup is not due and its directory has not changed. It writes, as before, on first contact, when the lookup is due (SessionStart, or 30 s since the last), when the directory changes, and to claim a delivery. On the host above that leaves 23.5% of hook events writing (21.5% a lookup that is due, 2.1% a changed directory, mostly subagents working in another folder).

`sessions.last_seen` and `sessions.cwd` are now as of the session's last write, up to 30 s before its last event. No hov command reads either column.

**Hook-path connections commit at `synchronous=NORMAL`.** The hook, `notify`, the idle watcher and the restart budget open the mailbox through one new function, `db_hook`. Their commits write the WAL and release the lock without waiting for the disk. These connections write bookkeeping only: session rows, delivery claims, read marks, the wake budget. After a power cut or an operating-system crash the last such commits may be missing, so a message may be handed over or shown as unread a second time. A process that dies loses nothing, and the database stays consistent.

Every other connection stays at FULL: `send`, the link and the MCP server, which store mail, and the commands a person or an agent runs (`inbox`, `ls`, `whoami`). A FULL commit syncs every frame written before it.

On an unlocked mailbox the hook is no slower: 150 hooks each, interleaved, median 62.9 ms before and 47.7 ms after (p95 98.4 and 53.9).

### Limits

- SQLite syncs the header of a WAL it has just created or restarted while holding the lock, whatever the setting. On a host where no long-lived process keeps the mailbox open, the WAL is created by each hook that writes, so that hook still pays one sync. Such a hook is now the exception.
- A command that stores mail still syncs under the lock. A hook that needs to write while one of those is stuck on the disk for over 2 s still logs one `hook-error` and exits 0; the next hook delivers. That path is unchanged, and so are the hook lines from 0.1.14 and 0.1.15.

### Tests

Two added (`test_hov.py`, fifty-four; one hundred and ninety-nine in all):

- With another connection holding the write lock, a known session's prompt and tool hooks finish at once with no error and leave its row untouched. A changed directory, a due lookup, SessionStart and pending mail each still wait and log one error. With the read-first path turned off the test fails on a 2.08 s wait.
- With every sync slowed to 1.5 s by a preloaded shim, a hook's three commits finish in under 1.5 s while `send` still waits for its sync. With the hook opening the mailbox the old way the test fails at 6.1 s. This half needs a C compiler and Linux and is skipped without them.
