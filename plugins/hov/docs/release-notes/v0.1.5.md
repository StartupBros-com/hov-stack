# hov v0.1.5

## Highlights

- A new session no longer starts with every broadcast the host ever carried as unread mail.
- A sender no longer gets its own `*` and `host:*` messages back.
- Mail a session has read, and broadcasts it sent, stay out of its inbox when its title changes.

## Details

A broadcast is now mail only for readers that were around when it reached this host's mailbox. hov records
each name's first contact in a new `names` table; a Claude Code session counts from its own first hook or
command, so a new session that reuses an old title also starts clean, in `hov ls` as in its inbox.
Every reader command counts as first contact, `hov ls`, `search` and `thread` included, and a `hov mcp`
reader counts from when it connects, so a broadcast sent while it is connected is its mail whatever
tool it calls first. Direct mail is unchanged: mail sent to a name before that name first appears
still waits for it.

"Around when it reached the mailbox" is arrival order, not a clock reading. Storing a message and recording a first
contact each take the next stamp from a one-row counter (`clock`) inside their write transaction, so stamps follow
the order writes commit in and no two are equal; the counter moves up to the wall clock whenever that is ahead, so
stamps stay near real time. A relayed message is stamped when it arrives, and every message still shows its sender's
timestamp. An earlier 0.1.5 draft compared wall-clock times. The WSL2 host hov was built on was seen stepping its clock
back by about 0.7 s several times a minute, and in a stress run that draft missed three broadcasts, each stored after its
reader's first contact but timestamped 602 to 612 ms before it. Going by the sender's timestamp also dropped a
broadcast that crossed a link after an outage for any reader first seen in between, and moved the line by however
far two hosts' clocks disagreed.

Before 0.1.5 a broadcast matched every reader whose read record did not name it. Read records are
kept per name, so each new session, each new title and the sender itself saw the whole broadcast
history as unread, and a session that read under its eight-character id saw that mail again once it
was titled, and so did a session that changed titles. A session now records each read, and each broadcast
it sends, under its eight-character id as well as its title, so a retitle brings back neither.

Upgrade: the first 0.1.5 command on a host does three things in one write transaction. It creates `names` and fills
it with every name the mailbox already knew (session titles and ids, readers, senders, direct recipients) at first
contact 0, so they keep every broadcast they had unread. It gives each stored message an arrival stamp equal to its
timestamp. It starts the counter above every timestamp and first contact already stored. A session that already
existed keeps the broadcasts sent since it started. On a copy of a working mailbox (136 messages, 62 sessions) the
first open, which upgrades it, took 0.11 s and the next 0.12 s, so the upgrade's cost disappears into process
start-up; `hov ls` showed the same unread counts before and after, and opening the upgraded copy again left the file
untouched. A `hov mcp`, `hov link` or `hov relay` process started before the upgrade keeps the old rule until it
restarts.

`hov notify` writes once, on a name's first poll, to record its first contact; after that a poll that finds nothing
still writes nothing, so the OMP extension's change gate is unaffected.

Limits: a message stored by a process started before the upgrade, such as a running `hov link`, has no arrival stamp
and is placed by its sender's timestamp. A broadcast a session sent before 0.1.5 has no record under its
eight-character id, so it comes back to that session after a retitle.

Regression tests run the real script against scratch mailboxes. Each first-contact, sender and retitle test failed
against 0.1.4, except the one for an MCP client that skips `initialize`. 0.1.4 passes that one because it had no
first-contact rule; it guards a gap in an earlier 0.1.5 draft. The arrival-order tests (a clock that steps back just
before or just after a reader's first contact, stamps following commit order, a hub whose clock is an hour behind or
ahead, a row a 0.1.4 process stores) failed against the wall-clock draft, except the last, which that draft also
placed by its timestamp. Against 0.1.4, which handed every reader every broadcast, they fail wherever a reader must not
get one; the two that use the counter or `names` table directly error.
Three existing tests now register their reader before the broadcast they expect.

Fixes [the broadcast backlog issue](https://github.com/StartupBros-com/hov-stack/issues/555).
