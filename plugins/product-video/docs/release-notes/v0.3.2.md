# product-video v0.3.2

## Highlights

- RecordedTour renders no longer run out of memory on many-core machines: at most 4 browser tabs and a bounded frame cache, and a new --concurrency option sets the tab count.
- RecordedTour verification no longer fails correct frames of real screen recordings, and it no longer calls timing proven when the source changes on one side only.

## Details

Changes since v0.3.0:

- **Bounded render memory (v0.3.1).** A RecordedTour decodes every source clip in every browser
  tab, and Remotion opens one tab per two cores (up to 8), so on a 28-core machine a 69 s cut of
  two sources was killed for memory at 4 GiB and at 10 GiB. `recorded:render` now passes Remotion
  half the cores, at most 4, and a 512 MiB frame cache; that cut then peaked at 2,471 MiB under
  a 4 GiB limit. `render` and `narrated:render` are unchanged.
- **`--concurrency <n>` (v0.3.1).** Sets the tab count directly, a whole number from 1 to the
  machine's core count. Lower it if a render is still killed for memory.
- **Blurred gray SSIM.** `recorded:verify` compared frames in RGB SSIM. H264's 4:2:0 chroma
  cannot carry thin coloured text, so on a real 69 s cut of two screen recordings (thin text
  on black) one pass of the source through the codec scored 0.80 to 0.89 against itself, and
  a correct frame failed the 0.85 floor. Frames are now compared as gray after a 1.5 px blur.
  The floor is 0.95, a gross-content check: correct frames scored 0.9813 to 0.9991.
- **Codec noise is not motion.** A neighbouring source frame counted as the same picture only
  at RGB SSIM 0.999, and codec noise between two copies of one picture scored lower, so a
  noisy copy could edge past the expected frame and fail it. A neighbour is now the same
  picture when no gray pixel differs by more than 8 levels, and only a neighbour that differs
  in the source can fail a point. Most noise copies stayed within 6 levels; a noisier copy
  counts as differing, but scored at most 0.0001 above the expected frame.
- **Proof needs both sides.** A point now proves timing only when it beats a differing
  neighbour on both sides of the expected frame. A source that changes on one side bounds the
  timing in one direction only: with the plan 15 frames late, the old rule passed such a
  point. Those points are now reported as timing not proven.

Checked with a mis-timed control: every clip's start shifted by -2 to +15 frames in memory and
classified by the old and the new rule. On the smoke fixture the new rule caught every
shifted point the old one did, plus 3 more. On the real cut at +15 frames it caught 5 of the
10 points where the shifted frame really differs, and failed none of the 38 where it is the
same picture. With true timing the smoke fixture still matches 12 of 12 points. The real cut
now passes a full recorded:verify run, but proves timing at 0 of its 48 points, because that
footage is static around every probe point. On three of the control's runs (smoke at 0 and +3
frames, the real cut at 0) the shipped code reproduced its outcomes and pixel counts exactly. One test expectation changed: a point whose only differing neighbour is unscored is
now not proven instead of a match. The offline suite passed at this release's commit on one
Linux host with pnpm 11 and Node 24.
