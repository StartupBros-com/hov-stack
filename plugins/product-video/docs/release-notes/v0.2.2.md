# product-video v0.2.2

## Highlights

- zod is now 4.6.7, past the memory-exhaustion advisory that covers zod up to 4.6.5.
- A scenario whose base URL or route path does not parse is now rejected with a validation message instead of crashing the check.
- Narrated scenario, telemetry, capture bundle and resolved manifest files with a key that would set the object prototype are now rejected instead of having that key dropped.
- A step with an unknown key now reports its other problems too, such as a prohibited selector, instead of the unknown key alone.
- Text limits in scenario and manifest files count characters, so a selector written in emoji can use its full length; SRT caption files still count each emoji as two.

## Details

Changes since v0.2.1:

- **zod 4.4.3 to 4.6.7.** Advisory GHSA-mrhx-c7xc-m3w5 (CVE-2023-54404)
  covers zod up to 4.6.5: validating a very large array can collect one issue
  per bad element until the process runs out of memory. product-video's
  schemas read scenario, telemetry and manifest files from your own machine,
  so the exposure was a malformed local file, not input from the network.
  4.6.7 is the version Remotion 4.0.543 already installs, and its published
  package differs from 4.6.6 only in its version number, so the plugin now
  carries one copy of zod instead of two. That also clears the zod 4.4.3
  versus 4.6.7 mismatch `remotion versions` reported in v0.2.1.
- **Long lists.** zod 4.6.6 checks a list's maximum length before reading its
  items. A narrated scenario with 121 steps now fails with one issue where it
  used to report 122. Every list in the narrated formats has a maximum:
  hosts, routes, steps, telemetry events, bundle route IDs, captions and camera
  overrides. The capture scenario and tour manifest lists have no maximum, so
  this does not bound them.
- **Malformed URLs.** The checks that compare a scenario's base URL and paths
  with `allowedHosts` called `new URL` directly, so a base URL or path that
  does not parse threw a `TypeError` out of validation instead of returning an
  error. That was already true in v0.2.1 for a bad URL on its own. Since zod
  4.5.0 it also happened when the file had an unknown key, which used to stop
  those checks before they ran. The checks now skip a base URL that fails its
  own format check, and report a route or navigation path that does not
  resolve as an issue on that path. Capture `goto` paths have no other format
  check, so for them this issue is what rejects the file.
- **Unknown keys.** Since zod 4.5.0 an unknown key in a strict object no
  longer stops that object's own checks. A click step with the selector
  `password` and an extra key used to fail with only the unknown-key issue; it
  now fails with that issue and the prohibited-control issue.
- **Length limits.** Since zod 4.5.0 a text limit counts characters, not
  UTF-16 code units. An emoji used to count as two, so a 300-character
  selector fits 300 emoji now where it fit 150 before. Plain text is
  unaffected. This covers the limits zod checks in scenario, telemetry and
  manifest files. The SRT caption parser keeps its own 500-unit limit and
  still counts an emoji as two, so an SRT cue holds about 250 emoji.
- **`__proto__` keys.** Since zod 4.5.0 a strict object reports a
  `__proto__` key in its own input as unknown. The strict narrated formats
  (scenarios, telemetry, capture bundles and resolved manifests) now reject a
  file that has one. The capture scenario and tour manifest formats still drop
  the key.
- **Tests.** The click and move test that pinned the old one-issue result now
  checks both cases: with an allowed selector an unknown key is the only
  issue, and with a prohibited selector both issues are reported, unknown key
  first. New tests cover the malformed base URLs and paths, including a path
  that starts with `//`, for both scenario formats. They fail on the old code
  with the `TypeError`. Others pin the emoji length limit, the `__proto__`
  rejection and the single issue for an oversized step list.

The offline suite and the setup check were run on one Linux host with pnpm 11
and Node 24. The setup check rendered and verified a 4.5 second video. Real
captures were not tried for this release.
