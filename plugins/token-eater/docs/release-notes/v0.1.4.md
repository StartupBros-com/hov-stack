# token-eater v0.1.4

## Highlights

- A delegate script that cannot create its temporary run directory now prints a JSON error and exits with status 2. In 0.1.3 it exited with status 1 and printed no JSON.
- Sessions run the same as before. The change matters only to something that reads a delegate script's output directly.

## Details

- **The delegate scripts and `apply-tool.sh` keep their output contract when `mktemp` fails.** `delegate-claude.sh`, `delegate-codex.sh`, `delegate-grok.sh` and `apply-tool.sh` promise one JSON object on stdout and a documented exit status, where 2 means the invocation failed. In 0.1.3 a failed `mktemp` ended each script through `set -e` with status 1 and nothing on stdout. Each now prints `{"adapter":"<name>","ok":false,"error":"could not create a run directory"}` and exits 2. `mktemp`'s own message still goes to stderr.
- **Sessions behave as before.** `run-session.sh` is unchanged. It runs `delegate-codex.sh` or `delegate-claude.sh` and treats any non-zero status as a failed invocation; a grok session calls the grok CLI directly. No script in the plugin calls `apply-tool.sh`, which is kept as legacy. In a session the new JSON error lands in `service-out.json`, and `service-err.log`, the file the session's failure message names, carries `mktemp`'s message as it did in 0.1.3.
- **Tests.** The delegate suite runs each of the three delegate scripts with a temporary directory that does not exist and checks the JSON and the exit status. `apply-tool.sh` has no automated test for this path. `consent-preflight.sh` and `validate-data.test.sh` now check their own `mktemp` calls, which already stopped through `set -e`.
