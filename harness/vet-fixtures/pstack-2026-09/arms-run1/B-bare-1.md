**What the change would touch directly**

`fingerprint()`'s output is assigned straight to `asset.digest`, and `digest` is used for exactly one purpose in this file: `AssetStore.findByDigest(digest)` in `registerAsset`, which implements identical-content dedup. Making the digest time-dependent doesn't just add noise — it breaks the one thing this code visibly does with it.

**Concrete breakage**

- **Dedup stops working.** Any re-upload of the same bytes will now miss `findByDigest`, so `storeBlob` runs again, a new `Asset` row is inserted, and `metrics.count('asset.dedup')` effectively goes dark while `asset.stored` inflates. That's a real behavior change, not a hypothetical.
- **Loss of scan-result reuse.** When dedup hit previously, `registerAsset` returned the *existing* asset — which may already have a scan verdict attached via `AssetStore.attachScan`. `handleUpload` unconditionally calls `queueScan(asset)` regardless, but with a fresh digest every time, you also get a brand-new asset id with no prior verdict, so a file already known to be clean (or already flagged malicious) has to pass through `ScanWorker` again instead of inheriting known history. If verdicts ever matter for moderation/security, this is a regression, not just wasted compute.
- **The stated goal may not even hold.** `lastModified` on a `File` is the underlying file's own mtime, not "the time of this upload." Re-selecting the exact same file twice (unchanged mtime) still yields the same fingerprint — the intended "different times → different fingerprint" doesn't actually happen. Conversely, identical bytes saved to a new file (new mtime) now hash differently, which breaks true duplicate detection for content that legitimately should dedup. So the change is both under- and over-inclusive relative to what's being asked for.
- **Type hazard.** `UploadForm.file: Blob`, not `File`. Plenty of legitimate producers of a `Blob` (canvas export, clipboard paste, `fetch().blob()`, in-memory composition) have no `lastModified` at all. If any such Blob reaches `handleUpload`, `file.lastModified` is `undefined`, and the digest computation either throws, silently coerces, or produces a non-distinguishing constant — defeating the purpose while adding fragility.

**The one fact that would make it safe**

Whether anything in the system — this dedup branch, storage/cost accounting, or scan-verdict caching — actually depends on `digest` being a stable, content-only value across separate uploads. If it's confirmed that **no one relies on identical bytes producing the same digest across uploads** (i.e., content-addressed dedup and scan-reuse are not required invariants anywhere, including server-side), then embedding `lastModified` is safe — you're just formally turning `digest` into a per-upload identifier instead of a content hash. As the code stands today, that fact is false (the dedup branch clearly depends on it), so the change should not go in without that confirmation — or without a compensating change to how `registerAsset` decides "same asset."
