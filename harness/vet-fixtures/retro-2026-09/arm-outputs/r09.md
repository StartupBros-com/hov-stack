## Findings, in order of severity

**1. `CLAUDE.md` — the generated-file rule has no teeth, and it's what caused the actual bug**
The task required adding `currency` to refunds. The source of truth is `src/db/schema.ts` (`refunds` has no `currency` field), which feeds `src/db/generated-types.ts` via `scripts/gen-types.ts`. The agent found `generated-types.ts` first (via a grep for "Refund") and hand-edited it, even though it's headed `// AUTO-GENERATED. Do not edit.` and `CLAUDE.md` line 28 already says "Never commit generated files by hand." `schema.ts` was never touched. The next regeneration wipes the field — exactly the bug the user reported.
- Add a navigation pointer in `CLAUDE.md`'s "Where things are" section: `DB types: src/db/schema.ts is the source of truth; run pnpm db:generate to produce src/db/generated-types.ts — never edit that file directly.`
- Add a guardrail: a CI step (`.github/workflows/ci.yml`) that runs `pnpm db:generate` and fails the build on a git diff, so a hand-edit or an unregenerated schema change is caught mechanically instead of relying on the agent reading the header comment.

**2. `eslint.config.js` / `.github/workflows/ci.yml` — two explicit CLAUDE.md rules are unenforced**
The agent added `findRefund` returning `any` (violates "Never use `any`") and imported `query` from `../internal/pg-driver.js` into `src/core/router.ts` (violates "Never import from `src/internal/*` outside the module that owns it" — `pg-driver.ts` even says "Owned by src/db" in a comment). Neither was caught because:
- `eslint.config.js` only loads `js.configs.recommended` with `no-unused-vars`/`prefer-const` — no `@typescript-eslint` plugin, so `any` is invisible to the linter. (`src/core/router.ts`'s pre-existing `Promise<any>` return type shows this has been silently tolerated before.)
- `.github/workflows/ci.yml` never runs `pnpm lint` at all — only `typecheck` and `test`. Even the existing rules aren't enforced in CI.
- Fix: add `@typescript-eslint` with `no-explicit-any: error`, add a `no-restricted-imports`/`eslint-plugin-boundaries` rule banning `**/internal/*` imports from outside `src/db`, and add a `pnpm lint` step to `ci.yml`. These are mechanical, syntactic rules — exactly the kind that belong in a linter, not in reviewer prose.

**3. `CODING_STANDARDS.md` line 9 directly contradicts `CLAUDE.md` line 16**
`CLAUDE.md`: "Prefer named exports over default exports." `CODING_STANDARDS.md`: "Prefer default exports for single-export modules." One of these is stale. Since the reviewer only reads `CODING_STANDARDS.md`, it will happily approve default exports that the implementation agent (reading `CLAUDE.md`) was told to avoid. Pick one policy and delete the other line — whichever file loses should say nothing rather than disagree.

**4. `CLAUDE.md` line 36 — stale check command**
"Run `pnpm test:unit` before every commit," but `package.json` has no `test:unit` script (only `test`). The agent hit `ERR_PNPM_NO_SCRIPT` and had to fall back by trial and error. Change the line to `pnpm test` to match the actual script name — this is a one-command lookup that should just be correct, since `package.json` is the real source of truth.

**5. `CLAUDE.md` lines 6–8 — `pnpm status-report` is a costly no-op**
It's mandated before *every* task, but it just `cat`s `docs/status-dump.txt`, a synthetic 419-line dump of unrelated module rows with no connection to refunds or currency. The agent burned a full tool call and context reading it, then correctly ignored all of it. Either drop the blanket instruction from `CLAUDE.md` (let the agent look at status output only when a task is actually about service health), or replace the mandate with a pointer conditioned on relevance.

**6. `package.json` — the `dev` script silences its own output**
`"dev": "tsx watch src/cli/serve.ts > /dev/null 2>&1"` redirects everything to `/dev/null`, so when the agent started the dev server to confirm the endpoint worked, it could never see a log line or an error — by design of the script, not by accident of the tool. This makes runtime verification structurally impossible. Remove the redirect (or add a separate `dev:log` variant that tees to a file) so an agent (or a human) can actually observe the server it starts.

**7. `docs/architecture/request-flow.md` — describes a layer that doesn't exist**
It states handlers live in `src/core/handlers/` and that "Handlers never touch the database driver directly," but no `src/core/handlers/` directory exists — `src/core/router.ts` calls the repo directly. This mismatch between the doc and the real layout likely made it easier for the agent to import `pg-driver` straight into the router: there was no handler boundary in the code to run into, only a doc describing one that isn't there. Update the doc to reflect the actual current structure, or note that the handler split is aspirational and where it will land.

**8. (Minor) `CLAUDE.md`'s `Result<T, E>` rule isn't followed by existing code**
`orderRepo.ts`'s `findOrder` returns `Order | null`, not `Result<T, E>`, despite the rule "every exported function that can fail returns a `Result<T, E>`, never throws." This is a judgment call about whether the rule applies retroactively — worth a line in `CODING_STANDARDS.md` clarifying scope (e.g., "apply to new/touched functions; don't block on pre-existing ones") so the reviewer doesn't have to guess, and so a future implementer isn't misled by the rule reading as absolute when the codebase already violates it.
