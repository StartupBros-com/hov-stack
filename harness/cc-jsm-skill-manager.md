Most of Will's `~/.claude/skills/` are managed by **`jsm`** (jeffreys-skills.md CLI, `~/.local/bin/jsm`, config `~/.config/jsm/config.toml`). As of 2026-06-17: 112 of ~119 skill dirs are jsm-managed; only ~9 are "saved (cloud)" — his deliberate keep-set that `jsm sync` restores.

**Root cause of skill sprawl:** `[auto_update] install_new = true` + daily 03:00 schedule auto-installed every newly-published Jeffrey skill. Set to **`install_new = false`** on 2026-06-17 to stop the inflow (auto-update still refreshes kept skills). If sprawl returns, re-check this flag.

**Prune durably via jsm, NOT by deleting dirs** — a naked `rm` of a skill dir can be re-added by auto-update/`jsm sync`. Correct: `jsm uninstall <skill> --offline` — works headless, **auto-archives to `~/.claude/skills/.trash/<skill>-v1-<ts>/`** (fully reversible), updates jsm's local DB. Reinstall anytime with `jsm install <skill>`.

**Headless limits:** network ops (`jsm list --saved`, `jsm login`, non-offline uninstall) can fail with "Not authenticated" in non-interactive shells (creds are encrypted, need interactive passphrase). Use `--offline` for uninstalls.

**Nightly updates and the local layer:** jsm refuses to update a skill whose files differ from what it installed (0.3.22 prompted, `User prompt error: IO error: not a terminal`; 0.3.36 prints `Local edits ... Nothing was changed`), so since dotfiles#2091 jsm only ever sees pristine skills. `skills-localize.sh` keeps a local layer over them: the local-tooling note (`local-tooling-note.md`, `local-tooling-note.codex.md` for Codex) as its own paragraph after the frontmatter of every jsm skill whose own markdown names beads/br/bv, NTM, Agent Mail or idea-wizard, and the content overlays in `skills-patches`, each 3-way merged onto whatever jsm installed, using the committed `.base/` copy of the upstream file it was written against (`.base/VERSION` names that jsm version; a file with no `.base/` copy is ours to add). Before writing, it saves each layered skill's pristine files under `~/.local/state/skills-localize/`. It layers three trees: `~/.claude/skills`, `~/.codex/skills`, and `~/.agents/skills`, the jsm mirror Codex CLI reads (codex 0.166.0 loads `~/.agents/skills` and the deprecated `$CODEX_HOME/skills`, observed 2026-10-29); the Windows Codex desktop app reads `C:\Users\<user>\.agents\skills`, which nothing here manages. The wrapper lists pending updates once (`jsm upgrade --list --json`), names every pinned skill (`pinned, not updated`), clears `__pycache__` from those skills in every jsm tree (jsm counts it as a local edit), then runs `skills-localize.sh unapply <skill>` and `jsm upgrade <skill>` for each; ExecStopPost's `skills-localize.sh apply` lays the layer over the new version. Nothing is held and nothing is force-installed, except a skill unapply cannot put back (exit 3, `reinstalling it with --force`): a layered skill with no saved pristine copy, or one still holding text the pre-#2091 whole-file layer wrote. `skills-legacy-overlays.txt` lists the hashes of those old files; until such a skill is reinstalled, apply and check leave it alone and print `DRIFT: <tree> <skill> still holds pre-#2091 overlay text (<files>)`, and unapply removes the old layer's added files before the forced install. To clear one by hand: `skills-localize.sh unapply <skill>; jsm install <skill> --force; skills-localize.sh apply`. Delete the list once check prints no such line on any host. A layered file edited by hand stops that skill's update (exit 4) and fails the unit with the recipe: `skills-localize.sh forget <skill> && jsm install <skill> --force && skills-localize.sh apply`, which discards the edit. A refusal on a plain skill still fails the unit. `jsm sync` no longer runs nightly; run it by hand after saving a skill to the cloud list from elsewhere.

**Layer state and the lock:** the state lives per tree under `~/.local/state/skills-localize/<claude|codex|agents>/` (`SKILLS_LOCALIZE_STATE` relocates the parent): `root` (the tree it belongs to), `manifest/<skill>` (each file the layer changed, the hash of what apply wrote, and whether pristine had the file), `pristine/<skill>/`, and `migrated/<skill>`. Before changing any file, apply saves a transitional manifest that recognises both the old text and the new, and saves the final manifest only once every write has landed; after a failed write the transitional one stays, so the next run can still tell each file's pristine, layered and hand-edited text apart. The manifests, pristine copies, sums and `migrated` markers are synced to disk before they are renamed into place, the live files apply writes before the final manifest, and the files unapply restores before it drops their state (hov-stack#593: a WSL VM stop seconds after an apply left a saved pristine copy empty, which read as a permanent merge conflict). `conflicts`, a report every apply rewrites, is not synced. `pristine/<skill>/.skills-localize.sums` holds each saved copy's own sha256. A copy that no longer matches is reported as `ERROR: the saved pristine copy of … is damaged or missing`, never as a conflict; apply and check leave that skill alone, and unapply exits 5 without restoring it, ahead of any hand edit in the same skill, which the wrapper reports like a hand edit. The sums sit inside the pristine directory, so an older copy of the script that rewrites or drops the copies takes them along, and stale sums never outlive the copies they describe. Without sums (state saved before #593, or rewritten by an older copy), only a missing or empty copy, or one holding a NUL byte, counts as damaged; an apply records the sums once it finds nothing to write and no conflict for that skill (`recorded <tree> pristine sums: <skill>`). `migrated/<skill>` records that apply has layered that overlay skill in that tree once. Until it exists, a file whose hash is in `skills-legacy-overlays.txt` counts as pre-#2091 text; once it exists, a live file equal to one of our overlays counts as upstream having adopted our text. Runs serialize on `.lock` in the state directory: a run waits up to 120 seconds for it, then exits 1. The wrapper takes it exclusively before each skill's unapply and holds it until jsm returns, handing the descriptor to unapply as `SKILLS_LOCALIZE_LOCK_FD` (skills-localize checks that it is open on `.lock` instead of locking again; jsm runs without it). An installer `apply` or `check` that starts in that window waits, then layers the new version; one that waits past 120 seconds exits 1, and ExecStopPost's apply catches up. `~/.gemini/skills` also gets jsm's mirror, but no layer: skills-localize does not touch it.

**Overlay conflicts and rebasing:** where upstream changes lines an overlay also changes, apply keeps our side for those lines, still takes upstream's other changes, and records the file in `~/.local/state/skills-localize/conflicts`. The nightly journal prints `overlay conflicts, our side kept: <tree> <skill>/<file>; ...`. To rebase one, run a worktree's copy: `scripts/skills-localize.sh rebase <skill> <N>`, with N the installed jsm version. It rewrites `skills-patches/<skill>`: the installed pristine becomes `.base/`, the merge becomes the overlay, `.base/VERSION` becomes N, and each file where our side won is named `kept our side in <skill>/<file>` for review. A file from the host's patches is rewritten in place under `<overlay>/skills-patches/<skill>`, outside this repository's review, and rebase says so. Read those hunks, commit, merge; the line clears on the first apply after dotup deploys the merge. The live copy refuses to rebase, since it would rewrite the deployed checkout. To add an overlay, copy the installed upstream file to `.base/<file>` and its version to `.base/VERSION`, then edit `<file>`. This public repository ships a `.base/` only for `papers`, whose MIT licence permits it; the other overlays and their `.base/` copies patch skills from a paid library and stay in the host's `<overlay>/skills-patches/` (NOTICE.md). Laid out like `skills-patches/`, its files add to this repository's file by file: a file only the host carries applies from the host's `.base/`, and where both carry one, this repository's applies and check prints `DRIFT: host patch ... differs from this repository's copy`. `SKILLS_HOST_PATCHES_DIR` names another directory, or none when empty; `SKILLS_PATCHES_DIR` set alone reads no host patches.

**Failure alerts:** `jsm-auto-update-wrapper.sh` streams output and emits a bounded native journal marker with the invocation ID, stage, fixed cause and up to eight validated skill names. `unit-failure-alert.sh` retrieves that invocation's marker even after successful `ExecStopPost` cleanup fills the journal tail. Discord gets fixed explanations and a local journal probe, never arbitrary JSM output. An unavailable or invalid marker produces a generic failure alert. `UNIT_ALERT_JOURNAL_LINES=0` bypasses all journal reads, including markers.

JSM retains the existing per-unit alert cooldown. Repeated failures can page after that cooldown expires; there is no persistent incident dedup because wrapper success alone does not verify the later cleanup succeeded. Manual remediation and a verified successful service run remain necessary. Backup and other unit failure alerts retain their existing diagnostics and cooldowns.

Jeffrey's skills degrade gracefully when their CLI tools (ntm/beads/cass/ubs/slb/giil) or sibling skills are absent — they fall back to Claude-native alternatives (Task tool, manual tracking) and never hard-block. So removing tool-gated skills doesn't break the ~52 skills that reference them. See [[cc-mcp-architecture]].
