# Claude Code and OMP: the bridge decisions

Date 2026-11-10. Settled after a survey of the open-source options, a verification pass against the sources at pinned commits, three independent designs scored by a judge panel, one synthesis and five refutation passes against it. The decisions are the author's. Nothing here has been built or installed yet; this file carries the shape, and Milestone 1 carries the first slice.

The setting: two hosts. The workstation (`wm`) runs Claude Code CLI 2.1.322, which is the daily driver, with its Agents view as the one control plane. The laptop (`xps-omarchy`, "the XPS") runs oh-my-pi (`omp`) 18.12.5, including a long-lived interactive session that owns a device project and must not be disturbed. The workstation already reaches the XPS over an SSH alias on the tailnet. The approved scope, chosen by the author from the options offered, is quoted verbatim where it binds a decision.

## Decisions

**One pull-only SSH bridge, `hov-bridge`, and no second control plane.** The workstation initiates every connection, to a forced-command gate on the XPS. Every cross-runtime action is an owned job or a mailbox note in a durable file ledger on each host. OMP runs bridge work as an isolated-profile print-mode worker. No listener opens on either host, nothing edits either runtime's settings, and the author keeps using Claude Code CLI and its Agents view; no separate CLI, server or TUI is added on either host.

- **Scope, verbatim.** "Enable the necessary adapters/configuration for messages, status, and task delegation within approved projects. Agents may manage jobs created through the bridge, but not take over or terminate your existing interactive sessions." And: both offered options "preserve each receiver's existing permissions; neither lets agents approve protected actions, change one another's permissions, or reroute denied work." Every boundary below maps to one of those clauses.
- **Build, not adopt.** The two shipped transports both cross the scope. Agent Relay v18.0.0 (Apache-2.0, commit `1db5530`) writes `crossSessionInbound: "accept"` into Claude's `settings.json` and installs a SessionStart hook with auto-allow permission rules (`crates/relay-node/src/relay/claude_settings.rs:16-20,44-46`, `.../claude/session_hook.rs:1-35`); its OMP side delivers as user-role input through `pi.sendUserMessage`, and identity is a shared `rk_live_` workspace key. omp-messenger v0.17.0 (commit `437c6ed`) has no Claude client, requires OMP `^18.16.0`, binds `0.0.0.0` behind one shared bearer token and delivers with `deliverAs: "steer"`, which interrupts the recipient. Neither can be run as transport only. Full survey in the table below.
- **Transport is the existing SSH path.** Milestone 1 may call the gate by path over the existing full-shell alias. The hardening the design wants, a second key with `command="hov-bridge-gate",restrict` in the XPS `authorized_keys` and `loginctl enable-linger` for the XPS user, changes security posture and is an operator decision (gate 1 below). The alias resolves over the tailnet by MagicDNS; the XPS has python3 3.14, node, bun, `systemd-run`, `loginctl` and `jq`; its user manager is running; linger is off; over a non-interactive SSH session `XDG_RUNTIME_DIR` is empty, so the runner exports it from the uid before calling `systemd-run --user`.
- **Components.** `bin/hov-bridge` on the workstation (Node, about 500 lines): `run`, `send`, `status`, `result`, `cancel`, `inbox`, `ack`, `accept`, `watch`, `reconcile`, `selftest`. `harnesses/omp/bridge/bin/hov-bridge-gate` on the XPS (python3 stdlib, single file, about 250 lines): fixed verb whitelist, schema check, receiver-side project allowlist, owner check, atomic writes, runner spawn. `harnesses/omp/bridge/bin/hov-bridge-omp-runner` (shell, about 80 lines): `systemd-run --user --unit hov-bridge-<id> -p RuntimeMaxSec=<deadline>` around `omp --profile bridge -p --mode json --max-time N` in a throwaway worktree, then schema-validates `result.json`. `harnesses/omp/bridge/profile/`: the `bridge` OMP profile, own sessions, auth and settings, no extensions. The line counts bound Milestone 1 only; upkeep is unmeasured.
- **No OMP extension in v1, and no push into any session.** An extension loads only at session start, so delivering into the protected session would mean restarting it; `pi.sendUserMessage` is user-role ingress and the documented `attribution: "agent"` option is unconfirmed in `SendUserMessageOptions` at 18.12.5; OMP has no idle event and no way to attach to a running session (`--mode rpc` starts a new process). On the Claude side, `$.prompt.submit` from a mod into a bypass-mode session would let a peer message drive tools with no human in the loop. So inbound messages are notes, read only when someone runs `hov-bridge inbox`, never injected into a conversation. If push is wanted later it is an explicit opt-in for a non-protected session that starts with the extension already loaded, using `pi.sendMessage` with a custom type and `deliverAs: "nextTurn"`, never `sendUserMessage`.
- **Agents-view story, as verified on 2.1.322.** `claude --help` has `--bg`/`--background` and `-n, --name` but no `--exec`; the `--bg --exec` shell-job row that newer CLIs document does not exist here. `claude agents --json` lists background sessions with `id, cwd, kind, name, pid, sessionId, startedAt, state, status`, and a background session started by a launcher rather than the TUI does appear with state `working`. Therefore: a Claude-side job runs `hov-bridge run` as a background shell task of the delegating session, which wakes that session when the job ends; whether such a task gets its own row in the Agents view TUI is unverified (Milestone 1 item 1), and on a CLI with `--bg --exec` the watcher becomes a named shell-job row. OMP-requested Claude work, once accepted, is a real `claude --bg --name bridge-<id>` session with a transcript and `claude attach`; blocked rows surface permission questions to the operator. Interactive OMP sessions, OMP subagents and unread notes are never rows. The Agents view is a research preview and `~/.claude/jobs/<id>/` is not a stable interface, so failure of the row story falls back to `hov-bridge status`.
- **Trust boundaries, one per clause.**
  - *Within approved projects:* both the overlay allowlist on the workstation and the gate allowlist on the XPS must name the project. The protected session's project is absent from both, and the gate refuses any cwd that holds a live non-bridge `omp` process. Profile isolation does not cover `<cwd>/.omp` or `<cwd>/.claude`, so worktrees come from allowlisted repos only.
  - *Manage only bridge jobs:* every job records an `owner`; the gate honours `status`, `cancel` and `result` only for the owner, and `cancel` targets only the unit `hov-bridge-<id>` or the session `bridge-<id>`. The gate has no verb that lists or targets other sessions, so no path exists to take over or terminate an interactive session.
  - *Receiver permissions stay authoritative:* OMP workers run in the `bridge` profile with a stricter-than-yolo approval mode; whether `-p` mode enforces it is unverified, and when it cannot be shown the runner records `permission_posture=unknown` and the result carries that label. Claude delegates run with `--permission-mode default`, `--settings '{"crossSessionInbound":"refuse"}'`, `--disallowedTools 'Bash(git push --force:*),Bash(gh pr merge:*)'`, a budget cap and a worktree; workers never merge. Those flags are copied from the loop wrapper's headless launch (`bin/claude-loop.sh:626`), not sourced, so drift there does not propagate.
  - *No approval relay:* an inbound OMP request lands `held`. Only `hov-bridge accept <id>` starts it, and because sessions on the workstation often run in bypass mode, `accept` is guarded three ways: a `Bash(hov-bridge accept:*)` deny rule plus a PreToolUse guard (deny rules apply in every mode), a TTY requirement with typed confirmation, and a refusal whenever `CLAUDE_CODE_SESSION_ID` or `BRIDGE_JOB_ID` is set in the environment. A denied job ends `failed:denied` and is never rerouted.
  - *Residual gap, unenforced:* nothing on the workstation can observe a Claude denial, so a model could delegate the same work to OMP by hand. The mitigations are the non-yolo profile, held-by-default and the runbook rule. This is stated here so that nobody reads the bridge as closing it.
  - *Identity from the channel, never from text:* the gate derives `origin` and `owner` from the authenticated key and ignores any origin field in the payload. The key identifies the workstation to the gate, not an individual session; any session on the workstation submits under it. Theft of the XPS key yields gate verbs plus `held` requests, nothing more.
  - *Exposure:* no listener, no Remote Control, no relay. Cross-machine Claude messaging is unavailable anyway while requests route through a gateway `ANTHROPIC_BASE_URL`; same-machine messaging stays as it is (`crossSessionInbound`, per-session inbox sockets, `isolatePeerMachines`).
- **Job semantics.** Four states as separate timestamped events: `submitted` (gate wrote the spool file atomically and returned id plus content hash; a transport receipt only), `acked` (recipient validated against allowlist and caps; for a note, an explicit `hov-bridge ack`), `started` (first worker event: an OMP json event, or the `claude --bg` session appearing in `claude agents --json`), `completed` (schema-valid `result.json` with status `ok|failed|cancelled|timeout|uncertain|expired`). Dedup key is a hash of origin, project, task and nonce with an atomic `mkdir`; a resubmit returns the existing job, the same key with a different payload is rejected. Deadlines are mandatory, 30 min default, 4 h maximum; never started becomes `expired`, no terminal evidence after deadline plus grace becomes `uncertain`, and a retry is a new job refused while the old one is non-terminal. Depth cap 1 (`run` refuses when `BRIDGE_JOB_ID` is set), concurrency 2 per direction, a daily cap. A missing or invalid `result.json` is `uncertain`, never `ok`. No mid-job steering in v1; a later runner could own an OMP rpc stdin (`follow_up`, `abort`), new process only.
- **Persistence.** Ledgers in `~/.local/state/hov-bridge/` on both hosts, never committed, terminal jobs pruned after 14 days, `reconcile` lazy on every CLI call. Ledger files survive reboots; in-flight jobs do not (transient units and background tasks die), and end `uncertain`. Host values (alias, key path as a path, project map with direction and `autostart=false`, caps, the protected-project deny list) live in the private overlay as `bridge.json`, edited in a dotfiles worktree through a PR, with no credential values; the public repo ships `bridge.example.json` with placeholders. `hov-bridge xps-install` copies gate, runner and profile to the XPS, refuses to overwrite foreign files and writes a version stamp. Fresh-clone restore: `install.sh`, the overlay, `xps-install`, the operator-applied `authorized_keys` line, `selftest`.
- **Deferred, each gated on real use.** Milestone 3's 60 s pull timer (`hov-bridge reconcile --pull`, a user unit under `harnesses/omp/bridge/systemd/`) is a schedule edit and waits for approval; without it the OMP-to-Claude direction is on demand through `inbox`. A count-only mod under `mods/omp-bridge/` (status line and toast with job and unread counts, never message bodies, never `$.prompt.submit`) is wired only by operator decision through `CLAUDE_CODE_PLUGIN_DIRS` and `reconcile-runtime-env`, with a stated metric (completions noticed more than five minutes late) and a rollback.
- **Coupling and upgrade canary.** OMP side: only `-p`, `--mode json`, `--max-time`, `--profile` and `--session-dir`, all present on the installed 18.12.5 binary's `--help`; latest stable is 18.18.7 and the changelogs between are unread, so the flags are re-checked against 18.18.7 before Milestone 1. Claude side: `--bg`, `--name`, the `claude agents --json` field names and name lookup. `hov-bridge selftest` runs from `harness-doctor`, not CI, and exercises the real `omp -p` path and `claude agents --json` field checks, exiting non-zero with a visible status line when a flag, field or row state changes; CI covers only gate parser tests, ledger state-machine and dedup units, and a loopback selftest. Nothing under `harnesses/` runs in CI today.
- **Delete the bridge when** OMP delegation sees fewer than five real jobs in 30 days or none in 90, when Claude Code or OMP gains a native cross-host peer path, or when the row story fails and status-only proves enough. Process artifacts, with consumer, gated feature, defect class and deletion condition: the ledger (consumer `watch`/`reconcile`/`status`; gates dedup, cancel and uncertain outcomes; defect class orphaned or duplicated remote work after SSH drops and reboots; deleted with the bridge) and `selftest` (consumer `harness-doctor`; defect class silent transport drift after upgrades; deleted with the bridge).

## Gates before Milestone 1

Three decisions are the operator's, and Milestone 1 does not start without the first:

1. The restricted forced-command key in the XPS `authorized_keys` and `loginctl enable-linger` for the XPS user. Both are security-posture changes. Linger is recommended while the operator stays logged in, since the user manager is already running.
2. Whether note-only two-way messaging is acceptable: no push into idle sessions and no delivery into the protected session in v1. Real push needs either an OMP extension, which touches the protected session on restart, or `$.prompt.submit` into a bypass session; both were judged a laundering or hijack risk.
3. If OMP cannot be shown to enforce a stricter-than-yolo posture in `-p` mode: accept XPS jobs at yolo inside a throwaway worktree with budget and deadline caps, or restrict delegation to read-only tasks.

## Milestone 1

One slice, about 300 lines, with no mod, no timer and no OMP-to-Claude direction: `bin/hov-bridge` (`run/status/result/cancel/watch/reconcile/selftest`), the gate and runner, the `bridge` profile, one allowlisted scratch project that is never the protected project, and the overlay file. Acceptance, each run and observed:

1. A submitted job shows in the Agents view while it runs, either as the delegating session's background task or as a row; if neither, ship status-only and record it here.
2. `result.json` round-trips as `ok`, and the four states appear as separate events.
3. Resubmitting returns the same job id.
4. `cancel` stops only `hov-bridge-<id>` and leaves a sibling unit running.
5. Killing the watcher mid-job, then `reconcile`, re-attaches it.
6. Stopping the unit without a result yields `uncertain`.
7. A job whose cwd holds a live non-bridge `omp` process, and a job naming the protected project, are both refused.
8. The gate refuses an arbitrary shell command.
9. Killing the SSH session mid-submit leaves no half-written file.
10. A note round-trip: `send`, then `inbox`, then `ack` on the other host.
11. Rebooting the XPS mid-job ends the job `uncertain`, never `ok`.
12. `hov-bridge accept` refuses from a session environment and from a non-TTY.

Exit: five real delegated jobs over a week with no orphans, then decide on the pull timer, the OMP-to-Claude direction and the mod.

## Options set aside

| Shape | Why not |
|---|---|
| Agent Relay v18.0.0 (`agent-relay` CLI, Rust core, Relaycast engine) | Edits Claude `settings.json` (`crossSessionInbound: "accept"`, auto-allow rules, SessionStart hook); OMP delivery is user-role via `pi.sendUserMessage`; shared-secret identity; needs a Relaycast engine plus TLS proxy per deployment. The `--delivery mcp` route avoids some edits but was not traced. |
| omp-messenger v0.17.0 | No Claude client; peer range `^18.16.0` excludes 18.12.5; `deliverAs: "steer"` interrupts the recipient; binds `0.0.0.0` behind one bearer; stars 0, no LICENSE file in the tree. |
| Orca (commit `6ea47e7`) | Needs its own `orca-ide` CLI and server beside Claude Code; headless startup reconciles agent hooks automatically, which is a posture change; isolation, worker-policy preservation and caller-scoped cancellation were not established. |
| Agent Deck and other session managers that launch and own the agents they show | A second control plane beside the Agents view; the 2026-08-07 decision retired multiplexer control planes (herdr, tmux, zellij, ft) because they assume one agent per pane while this harness fans out through subagents, workflows, background jobs and worktrees. |
| Claude Remote Control for cross-machine messaging | Unavailable while requests route through a gateway `ANTHROPIC_BASE_URL`, and it would not reach OMP anyway. |
| An OMP extension in v1 (`claude-bridge`, with a protected-session opt-in) | Loads only at session start, so it reaches the protected session only through a restart; the attribution option that would mark relayed text as agent-originated is unconfirmed in source; judged a write path into the protected session. |
| `$.prompt.submit` from a mod into a running Claude session | A peer message would drive tools inside a bypass-mode session with no human step; fails "neither lets agents approve protected actions". |
| An agent-radar classifier edit to show bridge jobs | Adds vendored-fork drift to a polling classifier that lists sessions by `/proc/<pid>/environ`, which does not see `systemd-run` processes; unverified for `--bg` rows. |
| The extension-based design (`omp-bridge`, judged 18.5) and the pure spool design (`ssh-spool-bridge`, judged 17.0) | The former's extension and `$.prompt.submit` paths were fatal for the judges; the latter doubled version skew by running a Node CLI on both hosts. Its single-file python gate was grafted into the chosen design (judged 20.5). |

## Verification ledger

Verified by running the command and reading the result, 2026-11-10:

- `claude --help` on 2.1.322: `--bg`/`--background` and `-n, --name` present, `--exec` absent. `claude agents --help`: `--json`, `--all`, `--cwd`, `--settings`, `--add-dir`, `--agent`, `--effort`, `--mcp-config`, `--model`, `--allow-dangerously-skip-permissions`.
- `claude agents --json`: an array of background rows with the fields named above; a launcher-started background session is listed with state `working`.
- `ssh -G` on the alias: MagicDNS host on the tailnet, port 22, one identity file, `identitiesonly yes`.
- On the XPS over non-interactive SSH: python3 3.14.8, node, bun, `systemd-run`, `loginctl`, `jq` present; `systemctl --user is-system-running` reports `degraded` (running); `Linger=no`; `XDG_RUNTIME_DIR` empty, `DBUS_SESSION_BUS_ADDRESS` set; `~/.omp/profiles` absent; the installed `omp --help` lists `--profile`, `--cwd`, `--mode text|json|rpc|rpc-ui`, `-p/--print`, `--session-dir`, `--no-session`, `--no-extensions`, `--no-ui`, `--max-time`, `OMP_PROFILE`; one interactive `omp` session plus worker brokers, a browser relay and a headless browser were live.
- OMP 18.12.5 docs and source at tag commit `d5cd750e41fede277f9eb933455da92a0738915e`, read through the GitHub contents API: extension locations and factory export, `sendMessage`/`sendUserMessage` semantics, events, managed timers, `registerTool`, rpc framing and process model, `-p`, `--profile` relocation and its non-isolation of project-level dirs. Latest stable 18.18.7 (2026-11-10).
- Agent Relay at tag v18.0.0 (commit `1db5530`) and omp-messenger v0.17.0 (commit `437c6ed`), source read only, nothing cloned, installed or run.
- Claude Code docs for cross-session messaging, background sessions, hooks and the mods API, read at the current docs.

Not verified, and named as such above: an Agents-view row for a background shell task on 2.1.322; `--bg --exec` semantics on newer CLIs; OMP `--profile` approval-mode enforcement in `-p` mode; `attribution: "agent"` in `SendUserMessageOptions` at 18.12.5; OMP flag and rpc diffs 18.12.5 to 18.18.7; `systemd-run --user` with the exported runtime dir over non-interactive SSH; reboot behaviour of either host; Orca's isolation claims.
