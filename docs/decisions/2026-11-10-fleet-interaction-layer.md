# The fleet interaction layer: mailbox, relay, launch and the router's part

Date 2026-11-10. Supersedes `2026-11-10-omp-bridge.md` (PR #528) the same day. That record put three operator gates and a twelve-item milestone in front of a pull-only bridge before anything ran; the author judged the gates ceremony and asked for a fleet-scale answer instead. This record carries a decision and a build order with an acceptance test per pull request, and no gates between them. Settled after a second survey (agent mail, the flywheel that wraps it, Claude Code channels, and the router's own code at pinned commits), one synthesis and five refutation passes against it. The decisions are the author's.

The setting: a fleet, two hosts today. The workstation runs Claude Code CLI 2.1.322 as the daily driver, with its Agents view as the one window. The laptop runs oh-my-pi (`omp`) today and will run Claude Code `--bg` sessions soon; a third host joins once a key exists. Every Claude Code request on every host rides hov-router (a better-ccflare fork the author controls) through `ANTHROPIC_BASE_URL`. Claude Code's native cross-session messaging is same-machine only, and Remote Control is off behind a gateway base URL. The author granted use of the laptop's ssh key on 2026-11-10.

## Decisions

**Build `hov`, a fleet mailbox and launcher, on Claude Code's own primitives, and adopt nothing.** `claude --bg -n <name>`, `claude agents --json`, plugin hooks and `.mcp.json` are the control plane. No new CLI, server or TUI to live in. The router stamps and lists; it never carries mail.

- **Why not agent mail, in its own terms.** `mcp_agent_mail_rust` v0.3.40 (commit `7d94ecf55dfa6a1ca157ee5ad7cf4dbfb1dd5b4d`) says of itself "Single-machine coordination... Not a distributed system" (`README.md:2043`). It has no server push: `/mail/ws-state` rejects WebSocket upgrades (`server/src/lib.rs:12084-12100`) and clients poll. Its HTTP mode carries one static bearer, accepts it as a query parameter (`server/src/lib.rs:12420-12427,12558-12575`) and ships no TLS (`docs/SPEC-threat-model.md:9-10,106`); identity is "self-asserted" (`README.md:1416`). Its setup writes SessionStart, PreToolUse and PostToolUse hooks into Claude's settings that run its binary on every edit and every Bash call (`core/src/setup.rs:1193-1320`). `agentic_coding_flywheel_setup` v0.10.0 (commit `aff6199215cf6396e3ace3053cad1dc4e26ce7cc`) runs that server as a localhost-unauthenticated user unit (install manifest lines 1870-1890) and launches swarms through tmux, which the 2026-08-07 "no multiplexer control plane" decision already set aside. Neither mentions a second host, a gateway or `--bg`. Both carry "MIT License (with OpenAI/Anthropic Rider)" (`LICENSE:1` in each); whether work done with Claude Code is "for the benefit of" a Restricted Party is a legal question the author has not resolved, so nothing is copied from either and the rider does not carry this decision. The flywheel's `[br-123]` subject convention is taken in spirit only, as `[repo#N]` thread subjects.
- **Delivery into a session is hook text and nothing else.** `hov`'s SessionStart, UserPromptSubmit and PostToolUse hooks return unread mail as `hookSpecificOutput.additionalContext`, framed as untrusted peer text. They never emit `permissionDecision`, `decision` or `continue`; a test asserts the output shape. When hook stdin carries `permission_mode: bypassPermissions`, the hook injects sender and count only, and the body arrives through an explicit `hov inbox` call, so peer text never rides a session that prompts for nothing. Bodies are length-capped and slash-command-shaped lines are stripped. The mods API `$.prompt.submit` is not used: it submits as the user and bypasses the native inbox policy. Native permission prompts gate every tool call exactly as before. Mail changes what a session reads, never what it may do.
- **Transport is outbound ssh from the workstation, a star.** Each host keeps its own SQLite mailbox with FTS5 under its state dir. A persistent user unit on the workstation runs `ssh -T <host> hov relay` per host, streaming mail both ways over stdio; no listener opens anywhere. Mail from the laptop to a third host, and a laptop-initiated send while the relay is down, depend on a reverse path that does not exist yet: UNVERIFIED, and PR 2's acceptance test rather than an assumption.
- **Idle wake for Claude Code sessions has two candidates, settled in PR 4.** A working session reads mail at its next hook event; an idle one needs a nudge. (OMP's idle wake shipped separately, in its extension; see the 2026-11-12 amendment below.) Candidate one is `hov channel`, a `claude/channel` MCP server (research preview in the docs read 2026-11-10): events arrive as `<channel source="hov">` context, queue while Claude is busy and are processed in order. It loads only with `--dangerously-load-development-channels`, in interactive sessions, after a full-screen confirmation, and `hov channel` never declares the permission-relay capability, since anyone who can reply through a channel that declares it can approve tool use. Whether channels work behind a gateway `ANTHROPIC_BASE_URL`, and whether a `--bg` session can show the confirmation, are UNVERIFIED. Candidate two is an `asyncRewake` hook, whose exit code 2 wakes Claude with its stderr; whether it wakes a fully idle session is UNVERIFIED. PR 4 keeps the candidate that passes and moves the other to the table below.
- **Remote launch is `hov launch`, and a launched session is a real Claude Code session.** `hov launch <host> <name> <cwd> <prompt>` runs `claude --bg -n <name>` over ssh with that host's own settings and permissions. Such a session is a real Claude Code CLI session routed through the gateway, the same class as the background jobs the workstation already runs under the router's operator-approved exception of 2026-10-07 (hov-router `AGENTS.md:7`); that wording predates `--bg`, so a one-line clarification there is part of PR 7 and the operator's call. `hov` lists, attaches to and reads the logs of sessions it launched; it never stops, steers or attaches to a session it did not launch, and `claude agents` on each host stays the window. Background sessions need a supervisor to outlive their ssh login and are stopped after about an hour idle: both are PR 3's tests, and `loginctl enable-linger` is the decision they settle.
- **The router stamps and lists; it never carries.** hov-router at `b469b65533107fa5ab94cde3fbd744af2b1059ea` reads `x-claude-code-session-id` into an in-memory observer (five-hour TTL, cap 10,000, not persisted, `packages/proxy/src/session-account-observer.ts:18-22,236-241`), stores the body's `metadata.user_id` as `requests.client_session_id`, and reads no source address (`apps/server/src/server.ts:2556-2568`). PR 7 adds a `client_host` column fed by a header each host sets through `ANTHROPIC_CUSTOM_HEADERS` in its settings `env` block (with `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`, so the `x-claude-code-*` hints reach a custom proxy at all), records the header session id as its own column, and serves an authenticated `GET /api/sessions` grouped by host and session. Whether the header session id equals the body session id, and whether both reach the router from a `--bg` session, are PR 7's tests. In the code, API-key auth is off while zero keys are active (`packages/http-api/src/services/auth-service.ts:170-194`), so the endpoint requires at least one active key; that describes the code, not any deployment. The router never carries, stores or rewrites mail (the body-rewrite precedent at `packages/proxy/src/proxy.ts:1304-1315` stays unused for this), never launches sessions, and the PR 8 dashboard pane shows sessions per host, not mail.
- **Codex and OMP read the same mailbox through `hov mcp`.** A stdio MCP server exposing whoami, inbox, send, thread, search and ls, wired where each agent reads its MCP config (`codex mcp add` for Codex, `~/.omp/agent/mcp.json` for OMP; the plugin root carries no `.mcp.json`, since Claude Code sessions have the hook), plus `hov notify`, a count-only block an OMP extension (`omp/hov-mail.ts`) prints into the run before each turn (since hov 0.1.4 also after each tool result and on a timer; see the amendment below). The `run-codex` wrapper first named here is dropped: draining bodies into an unattended prompt contradicts count-only delivery, and the `inbox` tool gives Codex the same mail when it asks (PR 5, hov 0.1.3). OMP's wiring is proven on the wire and under node with a fake host; a model inside headless Codex calling the `inbox` tool and answering from its result is verified live (hub, after merge, with the hov server's tools pre-approved in Codex's config, since headless Codex refused that call under its `approval_policy = never` without it); so is a model inside the interactive OMP session on the laptop seeing the block, reading its mail with the `inbox` tool and replying over the link (2026-11-11, after the operator restarted that session). Whether an OMP model acts on the block unprompted, interactive Codex, and the hov tools Codex has not called are UNVERIFIED until a live run. The long-lived interactive OMP session on the laptop receives mail it can ignore and nothing else, and only once it has restarted, since OMP loads extensions at startup and reconnects servers only on its own `/mcp reload` (or `/mcp add`, `remove`, `unauth`, `reauth`) and `/reload-plugins`; nothing watches `mcp.json`, and a subagent shares its parent's servers.
- **Amended 2026-11-12 (hov-stack#542, #543; hov 0.1.4): OMP mail reaches a run that is busy or idle.** OMP fires `before_agent_start` only when a user turn starts, so before 0.1.4 mail sent during a long run or an idle stretch waited for the operator's next prompt. The extension now also checks after each tool result, returning the block as `additionalContext`, and every three seconds on OMP's managed timer, sending a new block through `pi.sendMessage` as a non-interrupting aside: a busy agent sees it at its next step boundary, and an idle agent starts a turn unless OMP's plan mode or the user's Esc pause holds it. That revises the sentence above: the laptop session no longer only receives mail it can ignore, because a count can now start a turn. The bounds hold: the block is still a sender and a count, a body still needs an explicit `inbox` call, the extension grants and approves nothing, and a woken agent may do only what its own session already allows. A check runs `hov notify` only when the mailbox file or its WAL changed, or on every twentieth unchanged check. Proven under node with a fake host running the real CLI; not yet exercised in a live OMP session.
- **Same-host Claude-to-Claude mail stays native.** `SendMessage` and `ListAgents` already do it. `hov` is for cross-host and cross-harness traffic; a same-host `hov send` between two Claude Code sessions works but duplicates the native path.
- **Placement.** `plugins/hov/` in hov-stack: `scripts/hov` (stdlib Python, SQLite with FTS5; `scripts/`, not `bin/`, because claude.ai plugin distribution rejects a top-level `bin/`), `hooks/hooks.json`, `mcp/omp.mcp.json` and `omp/hov-mail.ts` (the OMP wiring; the plugin root carries no `.mcp.json`), `tests/` and a user-unit template. The plugin is inert until enabled in a host's settings; PR 1's spike loaded it for one session through `--plugin-dir`. Router changes land in hov-router. Host-specific values (host names, header values, key names) live in the private overlay; this record and the plugin carry none.

## Build order

Umbrella issue: hov-stack#529. Each PR carries its own acceptance tests and its own no-claim boundary; nothing waits on a gate.

1. `hov` core: mailbox, `send/inbox/thread/search/ls`, the three hooks, and a spike showing `additionalContext` delivery into a working `claude --bg` session on the workstation.
2. Cross-host link: the relay unit, the laptop install, the first cross-host message, and the reverse-path test.
3. Remote launch: `hov launch/ls/agents/attach/logs`, the logout-survival test, the linger decision.
4. Idle wake for Claude Code sessions: `hov channel` behind the gateway, the `asyncRewake` fallback, one kept (OMP's idle wake shipped with item 5 in hov 0.1.4).
5. Codex and OMP: `hov mcp`, `hov notify` and the OMP extension, an AGENTS.md snippet (the `run-codex` wrapper was dropped; see above). hov 0.1.4 (#543) added the extension's tool-result and timer delivery.
6. Advisory claims (`hov claim <path>`, overlap check, never a lock) and a `handoff` message kind.
7. hov-router: `client_host` column, header session id column, authenticated `GET /api/sessions`, the AGENTS.md clarification.
8. hov-router dashboard: a Fleet pane listing sessions per host.

Size: roughly 1,200 to 2,000 lines of Python across PRs 1 to 6, excluding tests, and a few hundred lines of TypeScript in the router. A range, not a count.

## What waits for one "go"

Every PR lands inert. One operator "go" covers enabling, and only enabling: the `hov` plugin in each host's user settings, the relay user unit on the workstation (and linger, if PR 3 shows a launched session needs it), the MCP server entries for Codex (`codex mcp add`) and OMP (`~/.omp/agent/mcp.json`) and the OMP extension in `~/.omp/agent/extensions/`, the router API key and the `ANTHROPIC_CUSTOM_HEADERS` line in each host's settings `env` block, and the one-line AGENTS.md clarification in hov-router. The laptop ssh key is already granted and is not re-asked. Pre-approving the hov server's tools in Codex (`default_tools_approval_mode = "approve"` on its `[mcp_servers.hov]` stanza) is not in that list: it is a separate operator decision, taken on 2026-11-11 for the hub's Codex after headless Codex had refused the `inbox` call without it, and it covers that server's six tools, `send` included, for every Codex run on that host. Another host's Codex is its own decision.

## Options set aside

| Option | Why not |
| --- | --- |
| `mcp_agent_mail_rust` v0.3.40 | Single-machine by its own README, poll-only, hooks on every edit and Bash call, licence rider unresolved. |
| `agentic_coding_flywheel_setup` v0.10.0 | Wraps the above and launches through tmux, retired here on 2026-08-07. |
| Agent Relay, omp-messenger, Orca, herdr | Set aside in the superseded record for crossing the approved scope; nothing has changed. |
| Channels as the only delivery path | Research preview, interactive-only loader, gateway behaviour unverified; demoted to a PR 4 candidate. |
| Mods `$.prompt.submit` | Submits as the user, bypasses the inbox policy, waits for idle; hooks only. |
| The router as mail carrier | Wrong layer: peer text would sit in the inference path, and the proxy would hold state it cannot verify. |
| Remote Control | Off behind a gateway base URL (v2.1.196 and later). |
| The pull-only forced-command bridge (PR #528) | Gated before anything ran; superseded. |
