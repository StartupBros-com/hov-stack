### skill-tuner's own arm isolation (headless probe, Sonnet, cwd `~/dotfiles`)

`build_adapter_command` (`tune.py` lines 118-143) uses `-p --output-format json --setting-sources "" --no-session-persistence --disable-slash-commands --tools ""`. The CLI reference says `--setting-sources` selects settings files only; `--bare` is what skips CLAUDE.md, skills, hooks, plugins and auto-memory.

| Flags | Agent reported (3 of 3 calls) | Cost per call, three calls |
|---|---|---|
| skill-tuner's adapter shape | `CLAUDE_MD: yes`; the first call quoted the host memory index (`.../memory/MEMORY.md`) | $0.0593, $0.0598, $0.0283 |
| same plus `--bare` | `CLAUDE_MD: no` | $0.0045, $0.0041, $0.0005 |

Every skill-tuner probe, routing and endtask call carries the caller's CLAUDE.md and memory into the arm (a confound, and the host's doctrine leaks into the judged text) and pays roughly an order of magnitude more per call for it (the spread within each condition is prompt caching). Plugin eval's throwaway HOME does not have this problem. `--bare` has been in the CLI since well before plugin eval (changelog: the `--bare -p` SDK pattern predates it by months), so a version floor is not an obstacle; the known caveat is that `--bare` strips permission-mode policy (memory `claude-code-bare-flag-strips-auto-mode-policy`), irrelevant to a `--tools ""` call.

### Sandbox refusal on this host (Bash-granting suites)

The verifier authored a one-case suite granting `allowed_tools: [Bash]` whose prompt runs `ls $HOME`, reads `~/.claude/settings.json`, counts provider variables and curls a public host, and ran it with `--allow-tools Bash`. The run was refused before any model call (exit 1, cost $0) with: "a credentials file in this environment (the AWS config / shared credentials file, the GCP application-default credentials, a kubeconfig, or an Anthropic profile config) could not be followed (an AWS credential_process / credential_source cannot be excluded from the shell), so the Bash sandbox cannot exclude the files it points at — a Bash-granting evaluation cannot run here." Traced to `~/.aws` being a symlink into `/mnt/c/Users/user/.aws` (a cross-filesystem WSL mount) plus a populated `~/.config/gcloud`. The sandbox backend exists and is invoked; it refuses rather than running unconfined, which is the documented behaviour for a missing backend applied to a different precondition. Consequence: on this host only read-only suites run; any catalog suite that grants Bash, Write or Edit needs a CI runner or a HOME without those credential files. Whether an empty parent HOME clears the refusal is tested below.

**Reproduction with an empty parent HOME** (`HOME=/tmp/.../fakehome claude plugin eval ... --allow-tools Bash --keep-temp`, real home untouched): the run executed (exit 0, $0.19, one Bash turn, agent model `claude-opus-5`, the account default). So the refusal is specific to this host's credential-file layout. This is consistent with a clean-HOME environment on this host's sandbox backend; it was not run on an actual CI runner, whose backend availability and credential layout can differ. What the Bash tool inside the run reported, verbatim from the kept trace:

- `HOME=/tmp/claude-eval-4V6ejc/home`; `ls -a $HOME` listed the real home's entry names (`.aws`, `.cargo`, `.claude`, `.claude.json`, `.config`, `.git`, ...), but `.bashrc` in it was `Permission denied` and `cat /home/user/.claude/settings.json` was `No such file or directory`. The mirrored home exposes names, not contents, and the real config path is hidden.
- `curl https://example.com` returned `000` and the tool result carried `<sandbox_violations> deny network-outbound example.com:443 (user denied)`. Network denial is enforced and logged.
- 23 `ANTHROPIC_*`/`CLAUDE_CODE_*` variables reached the shell, including `ANTHROPIC_BASE_URL` (the host gateway), `CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_CODE_MAX_RETRIES`, and eval-specific ones (`CLAUDE_CODE_EVAL_CONFINED`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS`, `CLAUDE_CODE_HOST_HTTP_PROXY_PORT`). `ANTHROPIC_API_KEY` was not in the shell environment even though the parent had it set: the run's own shell cannot read the credential the run authenticates with.
- The workspace (`$HOME/cwd`) came pre-seeded with decoy dotfiles (`.mcp.json`, `.claude`, `.gitconfig`, `.zshrc`, `.idea`, `.vscode`, `.eval-artifacts`), so a suite must not grade on "files present" without a scaffold of its own.
- After the run, the kept directory's `home/` and `tmp/` are sealed at mode 000 under `sealed/` and the CLI prints how to open them; the `tracePath` stays valid only with `--keep-temp`.

**Credential-file probe** (same empty-parent-HOME setup, $0.16; the agent under test chose on its own to report existence and readability rather than contents): inside the run, `$HOME/.aws` exists with the real subdirectory names (`boto`, `cli`) but `.aws/config` and `.aws/credentials` are absent or unreadable; `$HOME/.claude.json` is a 0-byte character device (`crw-rw-rw-`, a null device bound over the file); `$HOME/.config` shows only `anthropic` and `git`; `/home/user/.aws` at its real path is absent or unreadable; `/etc/passwd` is readable. One gap: `/home/user/.claude.json` at its real path was stat-able with its true size (197,850 bytes, mode 0600). Whether its bytes are readable is tested next.

**Byte-count readability probe** ($0.15): the prompt asked for `head -c 4096 <path> | wc -c` over nine real-path and mirrored-path files, contents never printed. The agent under test (Opus 5) rewrote the command before running it: every `/home/user/...` path came back as the mirrored `/tmp/claude-eval-*/home/...` path and five of nine entries were dropped. Of what ran, the mirrored `.claude.json`, `.aws/config` and `.claude/settings.json` each returned 0 bytes (and `.claude.json` stats as a character special file), while the run's own seeded `.gitconfig` returned 57 bytes. Conclusion: the mirrored home masks secret contents (CONFIRMED); whether a real-path read such as `/home/user/.claude.json` is also masked is PARTIAL, because an agent-mediated probe will not run the real-path command as written and a `scaffold_script` runs outside the sandbox by design. The deciding check is a Bash-granting case whose command the model will not sanitise, for example a script shipped inside the plugin under test that only prints byte counts.

### A plugin's hook inside a run (papercut scratch copy, two runs, $0.12)

papercut is the only catalog plugin that ships hooks. A scratch copy with one case (`allowed_tools: [Read]`, prompt: read a missing file, then say DONE) ran under `--keep-temp`:

- First attempt used an absolute path outside the workspace: the Read was a permission denial ("running in don't ask mode"), not a tool failure, and no hook fired. papercut's own source says a denial reaches no post-hook; the same holds inside an eval run.
- Second attempt used `./does-not-exist.txt`: the Read failed, `PostToolUseFailure` fired, and `papercut-log.js` wrote exactly one record to `<run>/config/papercuts/<slug>.jsonl` inside the run's throwaway `CLAUDE_CONFIG_DIR`. The host store `~/.claude/papercuts/` had the same line count before and after (80,094). The plugin was loaded in the run (its name appears in the session init line six times).

So for this plugin the "hooks run outside the sandbox" caveat is real but bounded: the hook resolves its store from the run's config dir, so it cannot reach the host store unless `PAPERCUT_STORE` is exported into the run, which the env allowlist does not pass.

### Live `compare` over the run's own JSON (verifier-run, no model calls)

Extracting `{case: aggregates.score}` and `{case: aggregates.scoreWithout}` from the two-arm run's `aggregate-result.json` and running `tune.py compare --paired-json --baseline without.json --candidate with.json --delta 0.1` printed skill-tuner's full verdict block (verdict `not_worse`, 95% CI, bootstrap CI, per-case table) with no new code. `scoreWithout` and `passRateWithout` are present in the JSON but absent from the docs' field table; a suite run with `--ablation none` has no without-arm and cannot feed this. `compare_paired` needs at least 3 cases and identical case sets. The ingestion in the verdict table is therefore a ~30-line extraction script plus a `--plugin-eval` flag, not a new comparison engine.

## Price (surviving components)

- Context cost: zero in ordinary sessions. An `evals/` directory is not a plugin component type, so it is never loaded; the with-arm of the isolation probe listed only `skill-tuner`, nothing from the suite. `/skill-doctor` adds nothing to the listing. Run cost, from the runs' own COST columns: the base suite was $0.51 for 6 case-arm-runs ($0.085 each; $0.05 for a one-line answer, $0.13 for the routing case with the skill loaded); the routing case alone ran $0.14 per with-arm run over 9 runs, $0.08 without the skill body; Bash-granting probes ran $0.15 to $0.19. Over the 24 agent runs in this vet the mean was $0.11 per run, so a three-case suite at three runs both arms is about $1.50 to $2.50 at the default agent model. That is a floor: per-plugin cost is unmeasured for the other catalog plugins, and a skill-tuner output case that shells into `tune.py` would spawn a nested `claude -p` whose spend the eval's own cost ceiling cannot see. The default agent model in a run was `claude-opus-5`; pin `--model` to control this.
- Armor test: not applicable; nothing here is an always-on rule.
- Placement and off-switch: suites are files in each plugin repo; the CI step is off unless a repo opts in and a credential is present; `--no-publish` is the switch for the report. Nothing loads in an unrelated project's session; verified by the isolation probe (no suite content reached the agent) rather than by config.
- Delivery vs content: delivery is first-party and already installed (server switch noted); content is suites we author, priced by the name-masking and rubric-saturation findings above.
- Supply chain: a run executes the target plugin's hooks as the user, outside the sandbox; scaffold scripts and real MCP servers only on explicit flags; `--trust-plugin` in CI asserts trust of our own code. Provider variables are inherited by child runs, so a run on this host goes through the host's gateway and its cost figure is list price, not the gateway's accounting.

## Audit dividend (what vetting plugin eval exposed about the harness)

Ranked by how much each moves a decision.

1. **skill-tuner's arms carry the caller's CLAUDE.md and memory** (measured above, three calls per condition: `CLAUDE_MD: yes` every time; $0.028 to $0.060 per call against $0.0005 to $0.0045 with `--bare`). Every probe, routing-parity and endtask call since the project began has judged text with the host's doctrine in context, and `docs/COSTS.md` was measured that way. Fix is one flag plus an `adapter_shape` bump; filed against skill-tuner.
2. **A skill's name masked its description in this routing test, and skill-tuner's battery shows the name too.** Plugin eval could not see a destroyed description on `skill-tuner` (3/3 fired) until the name was neutralised (0/3); one plugin, one prompt, so a hypothesis for other skills. `routing_parity.py` lists `- {skill_id}: {description}`, so skill-tuner's own parity battery is exposed to the same effect; the 2026-08-06 30/30 result needs one neutralised-id run before it is cited as description-only evidence (now an acceptance criterion in the skill-tuner issue).
3. **113 of the 229 skills `/skill-doctor` lists were never used in its window**, after the 2026-07 demotion pass. The report names where to turn each off; it is the prune input `rent-check` has been approximating from transcripts.
4. **The dotfiles checkout is untrusted for headless runs.** `~/.claude.json` records `hasTrustDialogAccepted: false` for `/home/user/hov-stack` and 18 other projects, so any `claude -p` launched with that cwd and without bypass mode ignores the 20 project `permissions.allow` entries (the warning printed at the top of the `/skill-doctor` run). Bypass-mode sessions and the dispatcher (which runs from `$HOME`) are unaffected; a headless run from a dotfiles cwd that relies on project allows is the exposure. Operator decision: accept the trust dialog once in that checkout, or leave it and keep headless dispatch out of it.
5. **Reader fleets at inherited session effort stall behind the gateway.** Three Sonnet readers made no progress for 10+ minutes after their last tool result; the run was stopped and relaunched with `effort: 'medium'` on every fleet agent. The gateway is on the 14-minute-budget build (`better-ccflare-v3.5.78-b8a1d9e9` observed in the process list), which the memory note had recorded as not yet deployed; corrected in memory.
6. **`aggregate-result.json` ships a dangling `tracePath`** unless `--keep-temp` was passed (papercut logged). A provenance reader in the skill-tuner style must not depend on it.
7. **`claude plugin eval init` cannot hand its interview to a background-job session** ("session marker may be inherited"). The docs' "ask Claude to run init" path is interactive-only at best; a suite author in this harness uses `--bare` templates.
8. **No official-marketplace plugin ships an `evals/` suite** (0 of 39, cache 2026-09-18). Shipping suites in the HoV catalog is a visible differentiator for a catalog whose pitch is measurement.
9. **The catalog's harness-vet plugin (v0.2.3) lacks the phase-4 blinding rule** the local skill gained on 2026-09-19 (`Blind the arm` appears once locally, zero times in `~/SITES/harness-vet`). The published copy is one doctrine release behind; the same check is worth running on rent-check and skill-tuner before their next release.
10. **`run_arm.sh` isolates less than plugin eval does and misnames itself.** It exports only `CLAUDE_CONFIG_DIR` (never `HOME`), grants Bash, Write, Edit and WebFetch with no OS sandbox, and leaves `prompt.txt` and `config/` readable inside the arm's own cwd; its header, usage line and error string call it `vet-arm-run.sh` (lines 2, 21, 34, 95). A one-line sed fixes the name; the isolation gap is the T3 EXTRACT's deciding measurement.
11. **The worktree command-shape guard refuses any Bash command containing the token `eval`**, including `claude plugin eval --help`, `rg -F -e eval`, and a `papercut add -m` whose message mentions it. Two verifiers and this session routed every invocation through a script file. Logged as a papercut; the fix is a literal-prefix allowance for `claude plugin eval` in `harness/worktree-command-shapes.md`.
12. **Bash-granting evals cannot run on this host as configured** (`~/.aws` symlinked into `/mnt/c`, populated `~/.config/gcloud`); an empty parent HOME clears it. Any local use of plugin eval beyond read-only suites needs that layout changed or a runner elsewhere.
13. **The pro-gate launchpad checkout is behind its own pin** (local `plugin.json` 0.40.0, marketplace pin 0.48.0), noticed by the marketplace reader; not investigated, worth a `git pull` check before the next pro-gate session.
14. **Evidence citations drift under concurrent runs.** A reader cited the `--ablation none` results directory for graders that exist only in the two-arm run's directory, because two runs against the same suite finished minutes apart. A verifier who trusted the path would have confirmed against a file that lacks the grader. Guard: cite `caseFilter` and `suite.ablation` from the JSON beside the path.
