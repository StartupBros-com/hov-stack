- The reader corrected three assumptions in the frozen digest. ## Documentary findings (file:line evidence in the read-workflow journal)

### Signing engine and completion
- Signing is tRPC-only. No OpenAPI v2 path signs a field (116 paths enumerated). `field.signFieldWithToken` (`packages/trpc/server/field-router/router.ts:616`) and the envelope sign route (`envelope-router/sign-envelope-field.ts:16`, comment: "unauthenticated public procedure route") are mounted on the bare `procedure` (`trpc.ts:391`), reachable at `/api/trpc/*` with rate limiting only. The recipient token, resolved by `prisma.recipient.findFirstOrThrow({ where: { token } })`, is the sole credential.
- Recipient tokens are returned by the API (`packages/lib/types/recipient.ts:23,52,79`; `distribute-envelope.ts` returns token and signingUrl). Recipient token = `nanoid()` 21 chars; API token = `api_` + 16-char alphanumeric id, stored as unsalted SHA-512.
- Action auth (ACCOUNT, PASSKEY, TWO_FACTOR_AUTH, PASSWORD) hard-blocks token-only signing (`is-recipient-authorized.ts:95,108,132,157` each require a userId). Adding action auth is gated behind the Enterprise `cfr21` flag (`create-envelope-recipients.ts:81`); removing it via `POST /envelope/recipient/update-many` is not gated (`update-envelope-recipients.ts:133`).
- Completion flips the recipient to SIGNED inside a conditional transaction, then a job seals the PDF: PAdES `ETSI.CAdES.detached` by default (`packages/signing/index.ts:48`), no timestamp authority or LTV unless `NEXT_PRIVATE_SIGNING_TIMESTAMP_AUTHORITY` is set (`tsa.ts:5-10`). Certificate page appended by default; audit-log page opt-in (`includeAuditLog`, `organisations.ts:117`).
- The V1 field path trusts a caller-supplied `isBase64` boolean with no content validation; the V2 path checks only the `data:image/png;base64,` prefix (`constants/signatures.ts:4`).
- The API has reject-on-behalf-of (permission-checked, audit-attributed) but no sign-on-behalf-of. The e2e suites test cross-team isolation only, never same-tenant recipient impersonation.

### Envelope API v2
- `POST /envelope/create` (multipart) creates DOCUMENT or TEMPLATE envelopes; recipients, fields, distribute, redistribute, item download (`?version=signed` silently returns the original before COMPLETED), certificate and audit-log downloads, folders, templates, direct links. Legacy `document/*` and `template/*` create endpoints and API v1 are deprecated with removal on 2027-03-01 (`migrate-to-envelopes.mdx:13`).
- `distributionMethod: NONE` produces signing tokens without sending mail (`document-email.ts:66-80`, `send-document.ts:335-350`).
- The docs' first-api-call page shows a `POST /envelope/{id}/distribute` shape and a four-value role table that do not match the code (`/envelope/distribute` with the id in the body; five roles including ASSISTANT). Minor doc drift.

### SDK and MCP server
- `--tool` is a real mount gate (`tools.ts` registerTool early return); scopes are empty; no resources or prompts are registered despite the scaffolding. Default server is `https://app.documenso.com/api/v2`; `--server-url` points it at a self-host.
- API key is accepted only via the `--api-key` flag when launched through `mcp start` (`cli/start/impl.ts:50,71` pass `?? ""`, which drops the env fallback), so the vendor's own README puts the key in plaintext inside the MCP client config args. `DOCUMENSO_DEBUG` would echo it to stderr.
- SSE transport binds `0.0.0.0` with no request authentication. stdio is the safe transport.
- Every tool returns raw API JSON with no size bound; the "download PDF" tools return a JSON envelope, not bytes. `formatResult` has a `search()` truthiness bug that leaves the non-JSON branches unreachable.
- No telemetry or hidden network calls in the SDK. The 39.7 MB unpacked size is TypeScript source plus a bun bundle that inlines express and stricli (devDependencies) plus a sourcemap. `bin/` is not committed; the npm-publish step is delegated to a Speakeasy reusable workflow pinned by tag, so the published bundle is not auditable from this repo.

### Self-hosting and operations
- Reference compose requires SMTP transport, from-name and from-address to boot (`compose.yml:41,50,51` use `:?err`); it pins `:latest` against the project's own "pin versions" guidance; `prisma migrate deploy` runs unconditionally on every start with no rollback ("restore from your backup", `upgrades.mdx`). First admin requires a direct SQL `UPDATE "User" SET roles`.
- Telemetry (PostHog: app version, installation id, node id, hourly heartbeat) is on by default and honours `DOCUMENSO_DISABLE_TELEMETRY=true` (verified in the sandbox log); `disableGeoip: false` is not reconciled with the docs' three-field claim.
- Community edition has no usage limits in code (`packages/ee/server-only/limits/server.ts:47-52` returns `Infinity` quotas when billing is disabled). Nothing in the T1/T2 path is Enterprise-gated except action auth (cfr21), CSC/QES signing, SSO, embed white-label, 21 CFR Part 11.
- Ops burden for a solo operator: Postgres, a p12 certificate, an SMTP provider with SPF/DKIM/DMARC for real counterparties, reverse proxy plus TLS, backups (pg_dump plus the p12, no shipped timer), manual release tracking. Documented minimum 1 CPU / 1 GB RAM; recommended 2 CPU / 2 GB.
- Docs drift: `render.yaml` pins Node 22.13.0 against a documented Node 24+ requirement; `docker.mdx` contradicts itself about the insecure example certificate fallback; Railway auto-generates a self-signed cert while Compose requires the operator to mount one.

### Supply chain (delivery vs content)
- Delivery: the Docker image is built with plain `docker build`/`push`, no cosign, provenance or SBOM; both `:latest` and version tags are mutable; the release path is any collaborator's git tag or `workflow_dispatch`. `Dockerfile.chromium` is not built by CI and runs an unpinned `npm install` on top of the published image. `@documenso/skia-canvas` (first-party fork) has an install script that fetches a native binary during `npm ci`.
- Content: the one vendored patch is a benign radix-ui menu fix; `scripts/` are local-only; husky hooks affect developers only, not the runtime image. The `CAFEBABE`/`DEADBEEF` encryption-key ARGs exist only in the installer build stage; the runner stage never carries them and every runtime read site throws on a missing key. A commented-out guard in `constants/crypto.ts` that would warn on the literal is dead code.

### Security probe: can the API token holder sign as someone else? (agent `security-probe`)
- CONFIRMED, 2 of 2 attempts: create a two-signer envelope, read the counterparty's 21-character signing token from `GET /envelope/{id}` (also present in the distribute and update-many responses and `GET /envelope/recipient/{id}`), call `field.signFieldWithToken` then `recipient.completeDocumentWithToken` with it. The recipient flips to SIGNED with a real timestamp. The audit log attributes the event to the recipient's name and email with `userId: null`; the only tells are `userAgent: curl/8.5.0` and `ipAddress: null`, both spoofable.
- Recipient action auth (ACCOUNT, PASSWORD, EXPLICIT_NONE tested) cannot be set at all on this deployment: 3 of 3 attempts returned HTTP 401 "You do not have permission to set the action auth" because the organisation lacks the Enterprise `cfr21` claim (`create-envelope.ts:268-275`, `create-envelope-recipients.ts:80-86`, `update-envelope-recipients.ts:80-87`). Only the empty array is accepted. PASSKEY and TWO_FACTOR_AUTH not individually exercised (type-agnostic gate, PARTIAL).
- Signing a field on a DRAFT envelope is rejected (HTTP 500 "must be pending for signing").
- Conclusion for the prior agent's proposed controls: "each person performs their own final signing action" and "the agent cannot approve its own request" are not enforceable inside Documenso Community Edition. Anyone holding the API token can produce any recipient's signature. The only real control is who holds the API token and what happens before `distribute`.

### Why the prior agent's plan is over-engineering, on the evidence
1. T1 does not need a signing service. The status quo output is an image of a signature on a PDF; a 123-line local tool produces that in a fraction of a second, and pyhanko adds a cryptographic seal with the same trust standing as Documenso's self-signed seal. Background only: UETA (Florida s. 668.50) and ESIGN define an electronic signature broadly, as a sound, symbol or process attached with intent to sign, without singling out cryptographic or platform signatures. Engineering observation, not a legal determination: a stamped image and a scanned wet signature are the same kind of artifact, and the practical constraint is the counterparty's acceptance, which neither approach changes.
2. The "authorization service" has no consumer today. The probe shows the backend cannot enforce its boundary, so only a token-withholding proxy could; that matters when a second principal prepares documents under the operator's token, which nobody does. The requirement underneath it, a human confirmation before `distribute`, is right and belongs in the harness's existing hook and convention layer (EXTRACT row), not in a new service.
3. Self-hosting buys nothing at the stated volume. Ops burden: Postgres, p12, SMTP with SPF/DKIM/DMARC, reverse proxy, backups, manual upgrades of an unsigned image. documenso.com Free includes the same API at 5 documents/month.
4. The MCP server is not a viable interface today (REJECT above); the SDK adds a beta dependency for six calls.

1. Outbound act-as-Will actions are gated by exactly one hook (`whatsapp-guard.js`); Gmail send, Slack post and any future `distribute` call run on the CLAUDE.md convention alone. If enforcement is wanted for signature requests, extend the whatsapp-guard pattern to Gmail send and the Documenso distribute call rather than building an authorization service.
2. Worktree guard defect dotfiles#436, sixth reproduction: this session called EnterWorktree while six workflow subagents were running in `/tmp`; four of the six reported losing Bash (three self-resolved within minutes; the T2 browser flow lost its entire run and had to be re-launched). Papercut logged.

Intake should label unread-mechanism statements as unverified rather than asserting them, since the digest is pasted into every prompt.
